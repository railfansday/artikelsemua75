It has been revealed that A data lake bucket held less than a terabyte and cost about $5 a day. On the day two new Databricks streaming pipelines went live, its cost rose to almost $19 a day, and S3 request costs made up 97% of it. The pipelines worked as written, the tables stayed fresh, and every dashboard stayed green. Two configuration defaults drove the extra cost, and the signal sat on the cloud bill, far from the pipeline code and its tests. A few lines of configuration fixed it, for about $5,000 a year. The two pipelines are Lakeflow Declarative Pipelines on Databricks, formerly Delta Live Tables, running in continuous mode, so they "process new data as it arrives" and never stop. Their source changes rarely. Every 35 to 70 seconds, each pipeline checked for new data, found none, and wrote down that it had found none. One of the two tables had never received a row. (Related: My Journey to a serverless transformers pipeline on Goo...)

Each of those notes costs requests. A streaming job records its progress in a streaming checkpoint, and it splits its state into one folder per shuffle partition. Spark's spark.sql.shuffle.partitions defaults to 200, and the checkpoint we looked at had 201 state folders. Each empty micro-batch listed and wrote files across all of them.

Recent findings suggest that S3 bills lists and writes at the same $0.005 per thousand, more than twelve times the price of a read. The bucket's own bill shows it: 76.2 million list requests cost $380.98 in one month, while storage stayed under $1 a day.

According to recent reports, the bucket also has versioning turned on. When the job cleaned up an old checkpoint file, S3 kept the file as a noncurrent version and added a delete marker. The bucket gained 60 million objects in a month, mostly checkpoint leftovers that nobody would ever read.

Industry observers note that continuous mode is a sensible choice when you want fresh tables, and 200 partitions is what Spark gives you unless you ask for another number. The people who built the pipelines made reasonable choices with the information they had. That information came from the code and its tests, and the cost of these two choices only appears at runtime, in the production environment, at production cadence, after days of empty batches.

According to recent reports, nothing in their daily view carried that signal. Tests and staging runs last minutes. The pipeline's own metrics highlighted fast, successful batches. The cloud bill groups the charge as "S3 requests" for a bucket that many jobs share, a line that no single team owns, and it reaches finance as a monthly total weeks after the change that caused it.

That gap is the subject of our earlier post on AI-generated code and cloud cost: whoever writes the change never sees what it costs to run.

The pipelines moved to triggered mode on a schedule that matches how often their data changes, with a handful of shuffle partitions instead of 200. The checkpoint fixes the partition count, so a latest count needs a fresh checkpoint, which costs nothing for a table with no rows. A lifecycle rule now expires noncurrent versions after a few days.

Recent findings suggest that A cloud team would usually find the lifecycle rule first, and on its own it saves about $4 a month. Almost all of the $5,000 a year sits in the pipeline configuration, which a data engineer owns. A cost tool that stops at the bucket settings misses it.

According to recent reports, the number we keep coming back to is the ratio: a few lines of configuration for about $5,000 a year, more than $1,000 a year per line changed. Few code reviews look at a change with that cost in mind. And the signal pointed straight back at the change that caused it:.
