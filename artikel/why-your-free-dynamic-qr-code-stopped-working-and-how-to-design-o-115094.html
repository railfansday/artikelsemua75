Why your "free" dynamic QR code stopped working, and how to design one that won't

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

It has been revealed that A QR code is a picture of some text. When that text is a URL, phones open it. That is the whole trick, and it explains most of the problems people run into with QR codes printed on menus, posters and packaging.

There are two ways to put a URL into a QR code.

According to recent reports, A static code encodes the final destination directly, for example https://example.com/menu.pdf. Nothing sits between the phone and your page. The code works for as long as that page exists, and no service can switch it off. The catch is that you cannot change it: if the menu moves to another address, you reprint. (Related: School sends out minibus to catch absent pupils playing...)

Recent findings suggest that A dynamic code encodes a short link owned by a service, such as https://short.example/abc123. When someone scans it, the service looks up abc123 and redirects to the current destination. You can change the destination at any time and count the scans, which is why businesses like them. (Related: Latest Update: Japan debuts a ‘dumbphone’ that doesn’t ...)

The redirect is a dependency. Whoever runs short.example decides whether abc123 still resolves. Many QR generators offer dynamic codes during a free trial, then disable the redirect when the trial or the subscription ends. The printed code still scans, but it now lands on an error page or an upsell screen. The owner usually finds out from a customer.

Industry observers note that nothing about this is technical. It is a billing rule placed inside the redirect handler, roughly:.

If you build a dynamic QR service, the fix is a design decision: keep billing out of the redirect path. Billing can decide who may edit a code or see new statistics. It should not decide whether an existing code resolves.

Two smaller choices help printed codes too:.

It has been revealed that if the destination will never change, use a static code: it has no dependency at all. If it may change after printing, use a dynamic code from a service whose terms say what happens to the redirect when you stop paying, and read that clause before you print 5,000 flyers.

Industry observers note that we built QRLifetime around that rule, and around a pricing choice. Paying a subscription for the whole life of a menu, a package or a sign, just to keep one QR code working, never made sense to us. An editable code is one row in a database and a redirect on a server. So with QRLifetime you can pay once for an editable code, and that's it: no renewal, no plan to keep alive. Static codes stay free and are generated in the browser, and teams who prefer a subscription for many codes keep their codes redirecting after they cancel.

Whatever tool you use, the question to ask is the same: who controls the redirect, and what happens to it when the bill stops?
