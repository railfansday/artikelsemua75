It has been revealed that your observability bill doubles every quarter, and half of the logs are never read again. Before you change tools, ask a better question: where should telemetry live? A growing answer is ClickHouse telemetry storage, a column-oriented analytical database released under Apache 2.0.

According to recent reports, two open source projects build on it: SigNoz and ClickStack (formerly HyperDX). This article follows the operating decision rather than the documentation: what do you gain, what do you lose, and when is it wiser to stay where you are? The facts come from the GitHub repositories and the official documentation, read on 11 November 2026. (Related: Showcase Your Projects in Spaces using Gradio...)

A note on honesty: span.observer has not deployed these stacks. The excerpts reproduce the cited sources, and we say what is left for you to check. To place the topic against other approaches, see OpenTelemetry and Prometheus and Dynatrace and Grafana.

Logs and spans look alike: many rows, almost no updates, filters on time and on a few fields. That profile suits a column store. It reads only the columns you ask for and compresses repetitive values, such as a service name, very well. (Related: Hugging Face Reads, Feb. 2021 - Long-range Transformers...)

It has been revealed that sigNoz puts it in its own words: ClickHouse is the central data store, and its compression is presented as excellent for cutting storage cost. We have not measured that ratio on your data, and it depends on its shape. Test a real sample before promising any saving.

The downside is well known. This is not a classic full-text search engine. What used to be simple becomes a matter of schema and sort keys.

It has been revealed that the neutral entry point is the clickhouse exporter of the OpenTelemetry Collector (contrib repository). Its README marks logs and traces as beta and metrics as alpha. That is a decision signal: do not trust critical metrics to an alpha component without a fallback.

Three options deserve attention. ttl defaults to 0, meaning no expiry. create_schema defaults to true, yet the README recommends false in production, where you then own the DDL. async_insert stays on by default to batch writes.

To go further on Collector components, read our tour of the contrib components.

Industry observers note that the default sort keys of the otel_logs and otel_traces tables start with ServiceName. The ClickHouse documentation warns that they probably do not match your access patterns, and advises picking 4 or 5 columns from your most frequent filters.

Industry observers note that that is the hidden cost. A search engine indexes everything and hides the question. Here you choose, and you pay for that choice in engineering time.

According to recent reports, sigNoz bundles logs, metrics, traces, alerts and dashboards. Its architecture places a Collector that writes to ClickHouse and an API server that queries it. According to the README, queries can use a Query Builder, PromQL or ClickHouse SQL.

Recent findings suggest that on licensing, the repository is mixed. The LICENSE file says content outside the ee/ and cmd/enterprise/ directories is under the MIT licence, while those directories fall under an enterprise licence. Read it before any production use: it sets contractual conditions for the code concerned.

Sources indicate that retention is the concrete point. By default, the documentation gives 15 days for logs and traces and 30 days for metrics. A change applies only to upcoming data, and a longer period recovers nothing that has already expired. Self-hosted, you set it under Settings then Retention Controls; on SigNoz Cloud it goes through support and changes the bill. For a real use case, see our article on AI agents with SigNoz.

Recent findings suggest that clickStack, formerly HyperDX, is published under the MIT licence according to the repository LICENSE file. The README describes it as a search interface for logs and traces on top of any ClickHouse cluster, with a simple search syntax and optional SQL.

It has been revealed that the approach differs from SigNoz. The all-in-one image bundles ClickHouse, the UI, an OpenTelemetry Collector and MongoDB. The documentation also says the UI can connect to an existing ClickHouse, and that collectors, database and UI scale independently.

In a recent development, careful: the overview page we read describes neither a TTL nor numeric limits. Retention is therefore a matter of your own ClickHouse configuration. The README recommends at least 4 GB of RAM and 2 cores for testing, which is not production sizing.
