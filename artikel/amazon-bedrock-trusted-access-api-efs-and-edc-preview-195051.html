AWS has made trusted-access administration generally available, but Anthropic’s first two programs remain previews that change how enrolled customers’ data is retained.

AWS introduced the general availability of Amazon Bedrock’s Trusted Access API on November 23, 2026, giving teams one workflow for discovering model-provider programs, checking eligibility, requesting approval, and managing enrollment. It has been revealed that the first offerings, Anthropic’s Enterprise Frontier Safeguards (EFS) and Enterprise Data Controls (EDC), are public previews, not generally available services. Both put flagged safety cases in the customer’s hands, but they use different storage arrangements. (Related: How to generate text: using different decoding methods ...)

It has been revealed that retention is the immediate planning issue. Joining the preview turns off zero data retention for the accounts or projects added. AWS also instructs participants to use a test account, send only test traffic, and exclude regulated data such as personally identifiable information or protected health information.

Amazon Bedrock’s Trusted Access API is generally available; Anthropic EFS and EDC remain public previews requiring eligibility and an AWS account-team request.

The distinction matters for deployment planning. A generally available administration API can expose programs whose own terms, implementation, and availability remain provisional. AWS warns that the EFS/EDC preview’s APIs, IAM action names, and endpoints may change before general availability.

According to recent reports, covered models include Anthropic’s Claude Fable and Claude Mythos, plus Claude Opus 5.5 and Claude Sonnet 5.5 used through the Cyber Verification Program (CVP). Teams following Anthropic’s tiered Claude cyber-access programs should treat trusted-access enrollment as an additional governance step, with its own approval and data-handling settings.

Amazon Bedrock’s Trusted Access API separates approval from enrollment: eligibility means a provider or AWS has approved participation, while enrollment determines whether the program takes effect.

Sources indicate that requests without a named project use account and organization settings. IAM policies and service control policies (SCPs) govern who can enroll, allowing central administrators to restrict who accepts provider terms.

Industry observers note that project targeting also has an application-side detail. The AWS C++ SDK 1.11.934 changelog, dated November 20, lists an optional projectIdentifier parameter for InvokeModel, InvokeModelWithResponseStream, Converse, and ConverseStream. It accepts a project ID or ARN.

According to recent reports, for the EFS/EDC preview, teams still need their AWS account representatives to submit the requested scope and identifiers. The common API standardizes administration; provider approval remains a prerequisite.

Anthropic’s EFS and EDC public previews differ chiefly in who controls retained storage and encryption, while both leave flagged safety-case review with the customer’s team.

AWS’s EFS/EDC storage comparison sets out the operational differences:.

Automated monitoring looks for patterns across requests, including deliberate misuse and agents exceeding their intended authority. Flagged activity creates a safety case for the customer to investigate and answer.

Industry observers note that for EFS specifically, AWS states neither AWS nor Anthropic human reviewers access retained inputs and outputs, and those inputs and outputs are never used for training. The retained content supports automated monitoring within AWS.

EFS is the more suitable option when ownership of the bucket, key, and storage audit trail is a requirement. That conclusion follows from the documented controls, but it also carries operational responsibility. EDC removes customer management of the storage infrastructure while leaving the safety-review workload intact.

EFS buckets also contain two different record types: readable inputs and outputs under transcripts/, and encrypted safety-review records under prefixes including slab/. Customer ownership of the bucket does not make every stored object human-readable.

Anthropic’s EFS/EDC public preview turns zero data retention off for the accounts or projects added, so covered content is retained in the configured destination. Other accounts keep their existing ZDR treatment.

AWS describes the preview as intended for customers already enrolled in EFS ZDR. Participants therefore need to review a concrete change in handling: EFS stores retained content in their S3 bucket, while EDC uses Amazon-managed storage.

The documentation also identifies aws_review as the data-retention mode used by EFS and EDC accounts. That setting’s name should not be read as a promise of AWS human review; AWS separately describes the EFS process as automated monitoring with customer-led case review.

Sources indicate that the practical sequence is to approve the retention change internally, establish the storage destination, and then enroll the intended test scope. Organization-wide participation warrants particular care because its reach includes future member accounts.

It has been revealed that AWS’s preview instructions explicitly exclude regulated test traffic. The GA label on the surrounding API is therefore insufficient grounds to send production PII or PHI into these previews.

Anthropic’s EFS/EDC public preview uses per-Region storage configurations, with the most specific configuration taking precedence: project, then account, then organization.

Teams need to distinguish three locations:.

During the preview, automated review covers covered-model requests made through US and EU geographic cross-Region inference profiles and the global cross-Region inference profile.

These distinctions make the bucket location only one part of a residency assessment. Security teams also need to examine inference routing and where automated review reads the retained content.

In a recent development, an unconfigured Region is another risk. For EDC-eligible participants, a Region without an EFS storage configuration can fall back to Amazon-managed storage. AWS says Amazon-managed storage is unavailable to EFS-only accounts, so teams should verify eligibility and the effective regional destination instead of assuming a universal fallback.

Amazon Bedrock’s EFS public preview accesses the customer’s bucket and key through the bedrock.amazonaws.com service principal, using the bucket and key policies the customer supplies.

Sources indicate that AWS’s launch announcement states that covered models stop being served 24 hours after Bedrock loses access to the key or bucket. Separately, the user guide indicates failed retention writes can be retried for up to 72 hours.

According to recent reports, those windows describe different behaviors. The write-retry window is not a promise of 72 hours of continued inference access.

The resulting operational implication is significant: KMS and S3 policy changes can affect model availability. Access revocation, key-policy edits, and bucket-policy changes belong in the same change-control process as other inference dependencies. Revoking retention access should be treated as a potentially service-disrupting action.

Anthropic’s EFS and EDC public previews carry no separate program charge, and AWS says they do not change model pricing, behavior, or rate limits.

EFS customers still pay standard S3 and KMS charges. S3 transfer charges also apply when automated review reads content from a bucket in another Region. EDC’s managed storage removes the customer bucket-and-key management burden; it does not remove the need for staff to handle cases.
