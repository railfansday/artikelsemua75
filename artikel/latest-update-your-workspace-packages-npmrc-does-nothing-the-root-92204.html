Four installs. Four hooks ran. The warning showed up twice, and both times in the one place where it could do nothing at all.

cryptostrapon asked this one in the comments on my last npm piece, and it is the sharpest edge in the whole series so far. He runs a workspaces monorepo where three files disagree. The root file states hooks may run. The package's own file, inside packages/a, says they may not. His user file says they may not too. From a root install, npm printed that it was ignoring the workspace config at packages/a/.npmrc, and the package's install hook ran anyway. His point was not that the root wins. We already knew the root wins. His point was that a check inside the package reads green and tells you nothing, because the root file plus env and flags are what decide, and the package file is not even part of the conversation.

Industry observers note that I rebuilt his shape and ran it on npm 10.9.4 with Node v24.22.1. The monorepo is one root package.json with a packages/* workspace, one package called pkg-a, and three config files that disagree about one setting: the user file and the package file switch install hooks off, the root file switches them on. In a recent development, the package carries one install hook that writes a marker file, HOOK-RAN.txt, with the time it ran. Two runs of every shape, and I kept the raw output for all of it.

Sources indicate that four installs, four markers, and the two runs of each shape agreed every time. The behaviour is steady, and the package file loses everywhere, including in its own folder.

Run the check at the root and npm is straight with you. It highlights the user value, true, with the note that the project overrides it, and then the project value, false. Ask for the single value and it states false. That is the value the root install will use, and the root install did use it: the hook ran both times.

What the root check never does is mention the package file. I counted. Zero mentions of packages/a in the plain config list, and zero in the JSON dump too. The file exists on disk, it states the opposite of the root file, and the check at the root behaves as if it is not there. That is the correct behaviour for the install, and it is a trap for the reader. A person who opens the package file, sees the hooks-off value, and then runs the check at the root to confirm it will read false and think the check disagrees with the file. It does not disagree. It is answering a different question: what will the root install do. The package file is not part of that answer, and the check gives you no hint that a file with the opposite value is sitting one folder down.

This is the part cryptostrapon was really asking about, and the answer is worse than "it reads green." There is no per-package reading to trust or mistrust. Stand inside packages/a and ask for the config, and npm prints the warning about ignoring the workspace config and then fails outright: ENOWORKSPACES, "This command does not support workspaces." Ask for the single value and you get the same warning and the same error. Two attempts, two errors, zero values returned.

So the check he described, a per-package check that reads green, is not a check npm will even perform in a workspace package. The command refuses. The warning is real and it sits right there in the output, but it sits next to an error, and the error is the actual answer: inside a workspace package, npm does not let you ask what the package's own file says. Anyone who believes they verified the package file by running a check inside the package folder either ran the check somewhere else without noticing, or read the warning as a verdict and stopped there. The warning is not a verdict. It is a note attached to a refusal. (Related: Latest Update: LA Noire 2 leak resurfaces after source ...)

In a recent development, he reported seeing the warning, and I want to be exact about where I saw it, because it did not show up where I expected. Across two root installs, the warning appeared zero times. The output was one line each time, added 1 package in 1s and then up to date in 2s, with nothing about the hook and nothing about the ignored file. The hook ran in silence both times, and the second run is the detail I keep coming back to: npm noted the tree was up to date and still ran the hook again, restamping the marker two seconds after the first run. "Up to date" describes the packages. It says nothing about whether their hooks ran, and here the hook ran anyway.

Recent findings suggest that the warning appeared only when I ran commands from inside the package folder, twice out of two per-package installs, and both times the hook ran anyway. So the warning highlights up at the moment you are standing in the folder whose file is being ignored, and the install that prints it still obeys the root file. It tells you the file is dead while doing exactly what the file forbids. That is not a gate. A gate stops something. This is a label on a door that is already open, and it only appears after you have walked through it from the other side.

One honest caveat: he saw the warning on the npm version he runs; on 10.9.4 the root install stayed silent. The warning's timing may differ by version, and I did not test his. But the outcome did not differ: on both, the root file decided, the hook ran, and the package file changed nothing. If you are waiting for a warning to tell you a package file is being ignored, you are waiting for a message that may never arrive before the install, and that arrives too late when it does.

What I do with the package file now is simple: I delete it. A file that does nothing but suggest protection is worse than no file at all, because the next person to open it will believe it. If hooks must stay off in a workspace, the setting belongs in the root file, in the environment, or on the command line, the three places the root install actually reads, and I verify it with a plain value read at the root before the install runs. The package folder gets no config file of its own, because a config file there is a note written to a reader who never opens it, in a folder where the check itself refuses to run.
