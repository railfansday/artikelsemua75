Recent findings suggest that 71 tests, 8 pull requests, 5 channels posting through an API and 2 that I post by hand. That is the pipeline behind this blog at the end of its build week. This log explains how it runs, what I got wrong on the way, and what I still cannot measure.

Industry observers note that one caveat first. I wrote this before the first scheduled post went out, so there are no reach numbers here. Those belong to build log #2. Everything below is about the machine, not the audience. (Related: Industry News: Politics Takes A Toll On Your Health — W...)

The design has one rule that everything else serves: nothing is published unless I merge a pull request.

Each week is one branch and one pull request. It contains five post folders, each with a post.md, an image and sometimes a short video, plus one long article like this one. A post folder is the unit of work. The text for every channel lives in the same file, under one heading per channel:. (Related: Tech Report: The ADHD Trait That Can Fuel Creativity — ...)

Because a post is a folder of plain files, the review is a normal code review. I can read the diff on my phone, change a sentence, and merge.

Recent findings suggest that four GitHub Actions workflows do the work. A fifth, for silent approval, exists but is switched off.

Two platforms can schedule by themselves, so at merge time the pipeline hands them the whole week: Facebook gets each post with a scheduled time, YouTube gets each video as private with a publish time. LinkedIn and Telegram have no scheduling for this kind of access, so a morning job posts whatever is dated today.

Every successful post is written to a file called published.json straight away. On the next run, anything already in that file is skipped. That one file is why I can re-run a failed job without posting twice, and it is the first thing I would check if something looked wrong.

Recent findings suggest that the check that gates every pull request is a 500-line Python script. It is boring on purpose. For each post it checks:.

Industry observers note that the banned-term list has one detail I like. The repository is public, so a plain list of "words I must never publish" would itself publish those words. The public file holds only SHA-256 hashes of the terms. The validator hashes each word of a post, and each pair of neighbouring words, and compares.

Recent findings suggest that there is a second check I added late and now consider essential: code that a post quotes must run. The post about Java's == operator claims that 128 == 128 is false for Integer objects. The file IntegerCache.java sits next to the post, with its expected output, and the validate job compiles and runs it. If the claim were wrong, the pull request would be red.

According to recent reports, I planned for six API channels. There are five. The plan listed Hashnode as an automated channel. When I checked its documentation before writing the code, the old endpoint redirected to an announcement: since 13 May 2026, every API request needs a paid plan. My rule is zero paid APIs, so Hashnode became a file that I paste by hand, exactly like X. The lesson is cheap but real: I read the official documentation of every platform before writing its publisher, and one of six had changed under me.

It has been revealed that the first banned-term list leaked what it was protecting. My first version of the list was plain text. It was caught in review, before the pull request was merged, and replaced with the hashed version above.

Sources indicate that "Private" is not a setting I can assume. I had planned around YouTube locking uploads from unverified apps to private. The documentation now states that restriction is gone. I do not believe either statement until I see what happens to the first real upload, so the runbook says to check it by hand.

The first comment may not work. On LinkedIn the blog link goes in the first comment, not in the post. Posting is documented for the access level I have. Commenting is documented under a different permission. The code tries, and if LinkedIn refuses, the post stays up and I add the link myself. I will know which it is after the first live run.

Three things stay with me, and not because they are hard to automate.

There is also a kill switch: a file named PAUSE at the root of the repository stops every publishing job. I can create it from my phone.

According to recent reports, next Saturday's article is a deeper version of this week's note on precision and recall: how to build a quality gate for LLM output, from two numbers to a rubric. Build log #2 follows a week later, with the first real numbers.

According to recent reports, the code is at github.com/nghiep-pham-ecosys/lab-to-prod. If you see a mistake in a post, open an glitch. That is what a lab notebook is for.
