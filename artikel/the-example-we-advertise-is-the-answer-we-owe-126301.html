2026-11-22 · 95 array examples, three encodings, four broken endpoints.

Recent findings suggest that when a machine buys an API call it has not bought before, it does not read your documentation the way a person does. It reads the 402 response, copies the example, and retries. The example in that challenge is not marketing copy. It is the request the seller is telling the buyer will work. (Related: Hugging Face Reads, Feb. 2021 - Long-range Transformers...)

Ours advertises input arrays in JSON shape:.

In a recent development, A GET URL can only carry a string. So there are exactly two encodings that can reach a handler: the comma form ?numbers=1,2,3,4, and the JSON form ?numbers=[1,2,3,4] — the example's own shape. (Repeated parameters ?numbers=1&numbers=2 are not a third form; the gateway keeps the last value, so a caller who tries it gets one number, not four.).

Population: every service whose published input example contains an array — 101 entries in the verified-example corpus, 95 measurable. For each one we walked the public door with a signed trial wallet and compared three requests:.

In a recent development, the GET answer was read twice, so a handler that disagrees with itself (a random generator) is reported as non-deterministic rather than as a verb difference. A 429 or an upstream failure is reported as not measured, never as a finding.

Three distinct root causes, all in the handler and none in the protocol:.

We already had a guard for exactly this hazard. It requires lib/ops's arr() — patched in October to try JSON.parse before comma-splitting — and it proves the array form and the JSON form produce the same answer. It was green, and it was right about what it measured.

In a recent development, it measured the wrong door. It calls the handler in-process, and its population is limited to files that require('lib/ops'). The four handlers above parse arrays inline; none of them is in that population. Handler-level two-form parity is not a claim about HTTP.

That is the recurring shape of this class of bug: a guard proves the layer it can see, and the promise lives one layer out. The fix is not a bigger guard on the same layer — it is a probe that speaks the callers' protocol.

Worth publishing, because each of these looked exactly like a finding:.

Sources indicate that none of that changes the four real findings, which were re-verified individually after each probe fix. It changes how much of the first sweep should be trusted: the report keeps the raw runs and names which rows were later cleared.

All four handlers now use lib/input-coerce, the module that has documented this exact hazard since October (asArray tries JSON first and falls back to commas; list turns an absent value into []). POST arrays and the comma form keep their previous answers; the advertised JSON form now works.

Deployment, in the same shape as every handler change here: per-file backup, node --check on all four, sidecar restart (loaded 1717 handlers, 0 failed), the handler-freshness guard to prove the running code is the code on disk, then the trial-refund guard on both doors (a rejected call costs nothing; a fresh wallet still gets five trials). Re-measured live with the same script and the same examples: all four now answer 200 on POST, comma and JSON.

Industry observers note that take the example out of your own challenge, put it on the URL exactly as written, and call it. If that call fails, you are not selling to the buyer who read your advertisement — you are selling to the buyer who reverse-engineered you. The first kind is the one you claimed.
