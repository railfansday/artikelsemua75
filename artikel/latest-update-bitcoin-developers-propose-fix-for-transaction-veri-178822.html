Bitcoin developers have proposed a new verification system that would allow lightweight wallets to independently authenticate transaction signatures recorded on the blockchain.

It has been revealed that the draft Bitcoin Improvement Proposal, submitted by developer Jean Pablo on Nov. 22, addresses a limitation in how wallets verify transaction information received from external servers. (Related: GTA 6 developer pays touching tribute to late mother by...)

The proposal could particularly benefit wallets such as Electrum, which supports Bitcoin's Lightning Network and relies on external servers for some blockchain information. (Related: Alaska Mileage Proposal → JAL Business Class...)

Right now, lightweight wallets can verify that a transaction was included in a Bitcoin block using a cryptographic proof tied to its transaction ID, or txid.

However, that identifier excludes witness data, which contains signatures and other information used to authorize spending under Bitcoin's Segregated Witness (SegWit) system.

Consequently, a wallet could successfully verify a transaction's inclusion while holding witness data that differs from what miners actually included in the block.

Pablo's proposal addresses this discrepancy by introducing standardized witness transaction inclusion proofs built around a second identifier, known as the witness transaction ID, or wtxid.

Unlike the conventional transaction ID, the wtxid incorporates witness data, allowing wallets to verify that the full transaction they received matches the version included in a mined block.

In a recent development, the proposed system connects that identifier to Bitcoin's existing witness commitment, which is recorded in the block's coinbase transaction. A second cryptographic proof then connects the coinbase transaction to the block header.

In a recent development, an ordinary proof checks the transaction ID. The draft adds a path from the witness data to the same block header.

A wallet can compare the witness data it received with what a valid block committed to.

According to recent reports, the proposed path assumes a valid block with a SegWit witness commitment. Chain selection and confirmation depth are separate from inclusion verification.

Together, these checks allow wallets to authenticate witness data without downloading and examining the entire block.

The development follows an earlier request from Electrum contributor SomberNight, who sought witness inclusion proofs to strengthen transaction verification for the wallet's Lightning Network functionality.

Lightning wallets interact with Bitcoin's underlying blockchain when opening, closing and monitoring payment channels, making reliable transaction information particularly important.

The proposed verification system would allow such wallets to independently confirm the witness data supplied by servers while continuing to operate without storing complete blockchain data.

The request previously prompted work on Bitcoin Core, where developers explored extending existing transaction proof commands to cover witness information.

That pull request closed in May without being merged, and developer Sjors Provoost later continued the effort through a separate implementation that introduced commands to generate and verify witness proofs.

Meanwhile, Bitcoin Knots introduced experimental witness-proof support in version 29.1, and Electrum developers have been working on related protocol changes.

However, these efforts use different proof formats, creating compatibility challenges between wallets and the servers providing blockchain information.

Pablo's proposal attempts to resolve those differences by specifying two binary formats and a JSON representation for exchanging and verifying proofs.

The first format provides a separate cryptographic proof for each transaction, while the second reduces duplicated information when verifying multiple transactions together.

In one example involving 10 transactions, the second format reduced proof data from 4,523 bytes to 3,325 bytes, approximately a 26% reduction.

The proposal also includes a Python reference implementation and 93 test cases designed to establish consistent verification behavior across software implementations.

Of those tests, 31 cover proofs that should be accepted, while 62 cover invalid proofs that verification software must reject.

The specification would give Bitcoin Core, Electrum and other wallet developers a common framework for implementing witness verification.

Pablo has requested feedback on the proposed formats and verification requirements, leaving developers to determine whether a shared standard can replace the experimental approaches already in use.
