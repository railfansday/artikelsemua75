Shared CXL memory pools come with steep software tax that could stall multi-server scaling

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Researchers at the University of Texas at Arlington and Intel measured what happens when four servers share one pool of CXL memory on real hardware. In a presentation shared at Supercomputer 2026 (SC26), they found that because the hardware doesn’t automatically keep shared data updated across servers, necessary software overhead adds a 3-5µ (microsecond) delay per lock, each time servers access the same data. These minute delays effectively cancel out the benefits — a finding that comes as CXL memory pools are being proposed as a potential AI KV cache solution.

Recent findings suggest that locks work like traffic signals for shared data: a server has to claim the lock before it changes something in the pool, and the other servers wait until it releases it. This way, no two servers overwrite the same data at the same time. Within a given server, the CPU’s hardware handles that handoff in a fraction of a microsecond, but across these servers, software is in charge of enforcement.

The setup comprises four 86-core Intel Xeon 6787P servers with 256GB of DRAM each, connected over PCIe 5.0 to one CXL memory box. The switch, which UT Arlington’s Peiran Du called “the only commercially available product we can use,” caps their setup at four servers. The catch is that there is no cross-host cache coherence or atomic operations on “a real four-host CXL shared-memory system.”. (Related: Accelerating PyTorch Transformers with Intel Sapphire R...)

This means no synced CPU caches and no hardware atomics between servers to build locks on, so software has to handle both. Writers publish their cached copy out to the pool and wait for it to finish, while readers throw out stale copies before reading, with the locks built from plain reads and writes, such as Lamport’s fast mutex. CXL 3.0 defines a hardware fix for the caches, called Back-Invalidate, but the researchers hadn’t received vendor confirmation that their platform supports it. Aside from the lock acquisition penalty, which is “roughly an order of magnitude higher than local hardware spin locks,” there is a visibility cost: “one-way cross-host visibility is about 1 µs.” This is 0.94 µs, one way, compared to 1.91 µs for an RDMA write on their 400Gb/s InfiniBand, so the link isn’t the cause. A local compare-and-swap takes about 100 ns and, across servers, a lock’s median is 3.7 µs if uncontended, but 132 µs at the 95th percentile with several servers on one lock.

The result: breadth-first search (BFS), a standard graph algorithm and a common benchmark, “gains nothing from adding a second host,” and was actually slower on four servers than on one, at 0.74s versus 0.55s. This was mostly not from the locks and barriers, which were only about 3.5% of its runtime, but due to the repeated flushing of shared state at every level.

Industry observers note that on the other hand, throughput for a hash table — using independent buckets and per-host allocators — grew almost linearly when adding hosts. Triangle counting, another standard graph benchmark, also had a runtime reduction of more than half when scaling from one to four hosts.

Sources indicate that those costs matter, in part, because shared CXL pools are emerging as a new home for KV cache — an AI model’s stored record of a conversation’s state — once it outgrows GPU memory and a server’s own DRAM. The CXL Consortium’s SC26 session description indicates cloud providers and GPU makers “have highlighted CXL memory pooling as an effective approach for improving KV cache access.”.

Sources indicate that SK hynix, which makes CXL memory modules, showed a design that hands KV cache between GPU servers through a shared pool and claims 2.6x faster time to first token than standard RDMA setups. Its abstract also claims 3.0x lower P99 latency and 1.9x higher throughput. Micron, at SC26’s CXL Pavilion, showed its Abaco reference design of pooled CXL memory shared across rack servers and GPUs. It claimed 10x to 30x agentic AI gains, with famfs support for apps like Nvidia’s Dynamo.

The need is real, even if efficiency gains have led to less cache needed per token. Vikram Sharma Mailthody of Nvidia Research noted at SC26’s Emerging Storage panel that his own analysis of open models on Hugging Face reveals KV per token falling “by 50% every twelve months” with “up to 78 times reduction so far,” giving the example that 128K context took “about 64 gigabytes” three years ago and now takes less than one. But context lengths are heading toward millions of tokens, and “the product of those two will keep increasing,” he said.

Agents also add to the demand. Earlier in the conference, a workshop talk by Argonne National Laboratory and RIT researchers, based on public AI serving traces, indicated that a “session calls again ~2 min later, once its tools return: a 160 GiB recency cache keeps 1% of its context,” needing the GPU to recompute the rest, or about 99%. Recomputation is significantly slower and more demanding, and memory is needed to cache more.

That makes it a capacity problem more than a speed problem. “Memory capacity is becoming a dominant factor. Memory latencies have not been seen as a primary problem yet,” Mailthody said. An agent’s context only has to survive a gap of a couple of minutes. It’s also ideal for any KV cache solution to be as inexpensive as possible, and given that a 128GB DIMM costs more than four times that of a 64GB DIMM last year. According to Intel’s Anil Godbole on SC26’s CXL panel, being able to add capacity past the DIMM slot limit — including reusing DDR4 — bolsters the case for CXL even further.

Recent findings suggest that it doesn’t hurt that the KV cache handoff is write-once, read-many, which is the type of pattern that actually scaled in testing, although UT Arlington did not specifically test KV cache. Researchers behind OCEAN, a CXL emulator, backed this idea in the same paper session as UT Arlington, saying that software coherence is fine for read-heavy work, with hardware essential as writes climb. Its abstract reports that hardware coherence, at least in emulation, can give an 11x improvement at full coverage on Tigon database workloads.

Sources indicate that limitations still exist, which is why SK hynix, for one, is relying on “novel locking and coherence protocols” for its design. Hardware isn’t quite there yet, and Back-Invalidate might “be pretty costly,” Du mentioned, suggesting that both hardware and software coherence may be required.

Industry observers note that micron, which built prototype KV cache sharing into Nvidia’s Dynamo, noted two primary failure cases in a CXL Consortium presentation last month: where the writer’s data never reaches the pool, and where the reader never sees the updates. The first can be fixed by producers flushing before blocks are published, so unflushed blocks can never be found. The second is fixed with a consumer flush, that is, invalidation of their cached lines, before reading. These are the fixes and costs that UT Arlington was measuring.

Micron cut its flushing cost by flushing each slot only once, which works because KV cache is content-addressed — a slot in the pool that hasn’t changed stays coherent after its first flush. Micron’s presentation also notes that neither failure causes a crash. Instead, the read returns plausible-looking data, and the output is wrong in subtle ways, with the wrong tokens on some requests under cache pressure.

Industry observers note that working against CXL as a solution is the fact that the memory pooling only reaches within a rack today, Godbole remarked; it doesn’t span a full data center. Marvell and Penguin Solutions, in collaboration and in addition to others like Lightelligence, have shown or announced memory expansion and pooling over optical links, which could stretch pooling past a single rack. CXL is also “not the protocol to ferry such major data,” Godbole added, as it’s built for smaller reads and writes, 64 bytes at a time, closer to how a CPU uses RAM. For bulk transfers, he said, RDMA is more efficient.

It has been revealed that A research system called Beluga, in a paper published on arXiv a year ago, had KV cache in “a commercial CXL switch-based memory pool” with time to first token cut by 89.6% and throughput raised 7.35x compared with an RDMA-based setup once its cache was filled. This suggests some optimization could improve the usefulness of the technology, too.

Sources indicate that CXL is clearly a hit or miss with how it is actually used being a main concern, with “a gap between the [CXL] spec and the implementation from different vendors,” according to UT Arlington’s Jia Rao. SK hynix’s second-generation CMM-DDR5, at 256GB and using CXL 3.2, has only been shown, and the device its KV cache design uses to select what to send is still what the tech giant’s Younghoon Min called a “research prototype.” These are early times, and the enterprise landscape is simultaneously changing promptly.

It has been revealed that on paper, shared CXL pools do fit the KV handoff idea, but until a commercial switch ships with confirmed coherence across servers, the best we have is KV cache numbers from vendor demos and research prototypes. Back-Invalidate should cut the software overhead UT Arlington measured, but Du expects it to add delays of its own; production systems would likely need a combination of hardware coherence and software approaches like Micron’s.
