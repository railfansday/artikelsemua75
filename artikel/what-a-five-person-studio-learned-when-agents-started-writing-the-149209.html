What a Five-Person Studio Learned When Agents Started Writing the Code

It has been revealed that I run a five-person AI studio in Lugano, Switzerland. We build software for small and mid-sized companies and keep several products of our own running at the same time. We could not carry that workload if we still typed every line ourselves. Coding agents now write most of the first version of everything we ship.

This article is about what that changed in practice: what we do during the day, where things go wrong, and why I stopped using the hour as the unit of work. (Related: Latest Update: How to train a newly introduced language...)

In a recent development, the research is more cautious than the vendors. In 2025 METR ran a randomized trial with 16 experienced open-source developers across 246 tasks. With AI tools allowed, the developers took 19% longer, and afterwards they still believed the tools had made them 20% faster. In February 2026 METR published a follow-up saying developers are likely faster now than in early 2025, while describing its own data as “only very weak evidence” for the size of the gain. Recent findings suggest that adoption did not wait for the answer. In Stack Overflow’s 2025 developer survey, 84% of respondents were using or planning to use AI tools, yet more of them distrusted the accuracy of the output (46%) than trusted it (33%). The 2026 edition asked the question differently. The most common answer, at 48%, was “I trust it when I can easily verify the output.”.

That answer matches what we see. On tasks where we can check the result in a minute, an agent saves us hours. On tasks where checking means reading everything it wrote, the saving shrinks quickly.

Sources indicate that anthropic’s 2026 Agentic Coding Trends Report describes software development as “shifting from writing code to orchestrating agents that write code.” In a team of five, orchestrating mostly means writing. A brief for an agent has to say what done looks like, what must not be touched and how the result will be checked.

A working day looks different as a result. Each of us runs several agent sessions in parallel, one per task, and moves between them: writing the next brief while one session builds and another waits for review. What limits how much we ship is the number of results one person can check properly in a day.

We tested this on ourselves. As an experiment we built a small browser game, which took 49 prompts over two days. Then we built six more test games from one shared brief, and after each one we wrote down what the brief had got wrong. Every game added a section to that list.

Sources indicate that we also learned that rules given in a chat get forgotten, by people and by agents. Our rules now live in the repository, in a file the agent reads at the start of every session: never commit secrets, add a changelog entry for every change a user will notice, upgrade the documentation in the same change that alters behaviour. The rules that matter most are enforced by a script. A hook blocks any attempt to write a credentials file into the repository, whether a person or an agent makes it.

Industry observers note that the documentation rule exists for a practical reason. The agent in the next session reads that documentation and acts on it, so a page that has gone out of date produces wrong work the following morning.

A recent Unite.AI article argued that agents need a written grant of authority enforced in systems, because with prompts alone “nothing enforces them.” Its author works at a multinational. We found the same at our size.

In a recent development, google’s DORA research describes AI as “an amplifier, magnifying an organization’s existing strengths and weaknesses.” The weakness it amplified in our case was review. When code arrives faster than anyone can read it, it is tempting to accept a passing test run as proof.

One of our six test games indicates the problem. It was checked in a headless browser, as the brief required, and it passed. Then a person looked at it. Everything on screen had been drawn in code, with no images and no models, and it looked poor. We are rebuilding that game from scratch. None of our checks asked whether anyone would want to play it.

The same applies outside code. We draft proposals and contracts with AI, and the failure we catch most often is prose that sounds machine-written: a clause that argues why a choice is clever, or a slogan where a fact should be. Clients notice it. Every document now gets a separate read for that alone before it leaves the company.

Sources indicate that the change I did not see coming was in how we count work. Some of our collaborators are paid by the hour. An agent can work on a task for twenty minutes while the person who rolled out it watches the screen. We had to decide whether that is billable time.

According to recent reports, we decided it is not. While an agent runs, we expect people to start the next task or pick up another project. A timesheet entry has to describe something a client would pay for, and a client in 2026 will hardly pay two and a half hours for translating a website. When I review hours, I put each entry next to the commit history and judge the output.

Industry observers note that with clients we went the same way. We quote a project at a fixed price against a written list of deliverables. If agents make us faster, the client does not pay for hours we never worked. If a brief was bad and we lose a day, that cost is ours.

Recent findings suggest that I do not think hourly billing disappears. Diagnosis, advice and a workshop in a client’s office are still fairly priced by time. For building software, though, hours used to be a reasonable proxy for effort, and effort for output. With agents doing the typing, neither step holds.

One question I have not settled is how to price the review itself. Reading and testing what agents produce is now the larger part of our work, and it is the part clients see least. How are other small teams putting a number on it?
