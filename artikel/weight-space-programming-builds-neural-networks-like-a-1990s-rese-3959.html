The writing aspect of WSP turns out to be quite a history lesson.

Weight-Space Programming still has me pretty intrigued. The basic idea is that frontier LLMs can read, write and edit the weights of neural networks. There's nuance to what's going on, but it feels like there's a lot of new ground to explore. (Related: Simple considerations for simple people building fancy ...)

In a recent development, in the original blog post, beyond the reading and editing experiments, the authors had GPT-6 Astra build a network to play Go from scratch, then improve it by playing practice games, and editing the weights based on analysis of its losses. That loop of writing, testing and editing feels like a newly introduced way to train a network, something like LLM Descent. But is it? (Related: How to train a latest language model from scratch using...)

In this article, I run my own weight-writing experiment with Claude Fable 5.2 on a familiar image classification problem. Look closely at what the model builds, and it turns out to be an interesting lesson in historical model-building techniques. With that latest lens on weight-space programming, I also study the Go network that Astra built in the original article, and find something very similar.

Recent findings suggest that MNIST is the OG image classification problem. The goal is to label each handwritten digit, 0 to 9.

In a recent development, similar to the Go test in the original Weight-Space Programming post, I built a test with a fixed CNN, then prompted Claude to write code that sets all its weights from scratch, with a few rules that include no fitting, regression, or searching. Drawing filters and templates by hand, from formulas or strokes, is explicitly allowed.

According to recent reports, it's a considerably stricter setup than Astra had for Go, with no PyTorch and no practice games, only its training loss, accuracy and confusion matrix after each attempt. The tests in this blog post were run with Claude Fable 5.2, which performed much better than Opus 5.5.

Sources indicate that claude's code runs in a sandbox that can only import NumPy, SciPy and math. Once it returns the weights, a test harness runs the network on the training and test images.

Industry observers note that claude has up to 50 steps, and at each one it sees all the feedback so far. The training set is 10,000 images from MNIST's official training split. Claude never sees the 10,000 official test images or how it scores on them, and the network with the lowest training loss gives us the final test score.

Though I have early stopping configured to stop when the training loss stops improving, all three runs descend for the full 50 steps, still improving when they run out, and land around 90% on the test set. Amazingly, that's close to where a training run with Adam gets to after 50 gradient steps.

In 1998, LeCun's paper that introduced MNIST described that era's approaches thus far as "a fixed feature extractor and a trainable classifier", where the feature extractor "is often entirely hand crafted" (LeCun et al., 1998). Accuracy, he wrote, "is largely determined by the ability of the designer to come up with an appropriate set of features", which is "a daunting task which, unfortunately, must be redone for each fresh problem.".

In a recent development, that daunting task is exactly what Claude takes on. All three runs built the same kind of pipeline, though not from the same parts:.

The first step at which each run's network uses the technique.

Let's follow run 1, step by step, based on Claude's replies and reasoning. It's the best of the three, at 91.3%, but the other two follow a similar path, measuring their way from hand-drawn templates to a classifier.

Claude starts like a 1990s computer vision engineer. Its first layer is a set of line detectors at four angles, written from formulas. They're cousins of the Sobel filter, a classic way to find edges in an image, which 1990s digit recognisers started with (Favata and Srikantan, 1996).

Each detector is a 5×5 grid of weights in the first convolutional layer. The way a conv layer works is that each filter slides across the image, multiplying the 25 pixels under it by its 25 weights and adding them up, so it scores high wherever there's a stroke at its angle, and zero on blank paper. Fable fills in four of the layer's eight filters this way and leaves the other four at zero for later.

Its second layer adds up each detector's map over patches of the image, so every image ends up as a 4×4 grid of cells saying which stroke directions appear in each.

Then it draws each digit by hand, as a few strokes in code, and turns each drawing into the same kind of grid: how likely each stroke direction is in each cell. Those tables become the final layer's weights, so it scores every image against all ten tables.

The final layer is a 10 by 256 grid of weights, with one row for each digit's table.

The weights are the log-odds of that table, scaled down by a temperature.

The log-odds turn each probability into a score that can simply be added up, and the temperature turns all the scores down, so the network isn't overconfident.

This is template matching - one of the oldest approaches in character recognition (Mori et al., 1992). The scoring works like naive Bayes, which treats each feature as separate evidence for each digit. Bayesian rules for reading characters go back to 1957 (Chow, 1957).

Its first network gets 71% on the test set. Redrawing the digits the confusion matrix claims are wrong brings it to 77%.

At step 3, it fills its four empty filters with corner detectors, and combines them in conv2's empty channels into a loop detector: four corners around a blank middle.

A researcher might have studied the digits to see where their features go wrong. We haven't given Claude the ability to do that in this test, but at step 4, it tries an interesting approach, where it stops classifying for a step and tests a loop detector (a feature for closed loops, like the ones in 0, 6, 8 and 9) on its own:.

I cannot tell that from a confusion matrix where everything is mixed together, so this step tests the detector on its own, like a unit test.

Recent findings suggest that it rewires the output layer so that each "predicted digit" means how strongly, and where, the loop detector fired. Each row of the confusion matrix then becomes a histogram of the loop detector for one true digit. One step later, it knows the detector fires on 83% of 8s. At steps 6 and 7, it tests its own drawings the same way, putting variants of each digit head to head.

In a way, this is kinda cheating, but then again it doesn't break the rules. The code doesn't run the network or fit anything, or even see an image. And hey: the test set is untouched, so the scores are still honest.

It has been revealed that next, it turns the corner detectors inside its loop detector into features of their own: four corner shapes where strokes meet (┌ ┐ └ ┘). It frees four of conv2's loop channels to carry the corner maps, and gives the final layer a weight for each corner in each half of the image. Handwriting recognisers relied on shape features like these (Trier et al., 1996) (Favata and Srikantan, 1996). At first it guesses how often each one reveals up in each digit. When that stalls at about 81%, it measures them instead, three steps in a row, and sets their weights from the results.

Three measurement steps on the corners gave more than many steps of guessing, and they showed that some of my hand-drawn expectations were far off.

According to recent reports, by step 18, it's at 83%. Pretty incredible, if you ask me.

From here on, the convolution layers never change. Every measurement, and every fix, happens in the final layer.

So it measures everything else too. Over the next twelve steps, it reads out how often each of its 32 stroke features fires on each digit, three at a time. At step 24, it plugs in the first fifteen measurements to check they help, and accuracy jumps from 83% to 88%.

At step 31, it throws its hand-drawn templates away completely.

rebuild the whole classifier from measured rates: 32 orientation cells, 8 corner zones and the loop detector. No hand-drawn stroke templates remain in the final layer.

What's left is a naive Bayes-style classifier, with every probability measured from the training set, one feature at a time, through the confusion matrix. In other words, it's fitting a classifier by hand. It reaches 89%, then 90% after tuning a few global settings. Then it spends steps 36 to 40 measuring the half of the stroke grid it hadn't covered yet.

Sources indicate that the last ten steps are fine-tuning by hand, scaling groups of the final layer's weights up and down to decide how much to trust each kind of evidence and how confident its predictions should be. It also keeps track of exactly how it will be scored.

It finishes at 91.3% on the test set, which is roughly where 50 steps of training with Adam gets us. It's not quite a like-for-like comparison, though: Adam's 50 steps see 64 images each, 3,200 in total, while Claude gets scores over all 10,000 training images at every step.

Opus 5.5 reaches for the same toolbox, with stroke detectors, hand-drawn templates, nearest centroid (picking the closest template), naive Bayes, and loop and endpoint detectors. The difference seems to be how much it measures. Fable spent far more steps measuring than Opus, which tended to prefer guessing. Opus also didn't manage to get a score beyond 74% on the test set. I also ran a few tests with Opus 5.5 that gave the model more feedback, including example digits, but they didn't make much difference, so I've left them out of this post.

Each step folder has the reply, thinking summary, code and metrics.

I ran the same test on photos from Kaggle's famous Dogs vs. Cats competition, with an image size of 64x64, using a slightly bigger fixed CNN (24,898 weights), the same rules and the same stopping rule. Here we can see some of the limitations of the hand-crafted feature approach, and some of the potential upper bounds of "weight-space programming".

Sources indicate that fable 5.2 takes the same initial approach as it did on MNIST, building a bank of hand-designed detectors, including pointed ears, an eyes-and-nose triangle and grass, then testing some of them one at a time. But those ideas don't bear much fruit:.

The ear probe highlighted the opposite of my guess.

Industry observers note that what does work is studying properties of the photo rather than the animal: dog photos have more green (grass and outdoor scenes), more texture, and more vertical edges. Its best network, at step 9, uses just those three. Nothing it adds after that does better, so the run stops at step 17.

It lands at 61.6% on the test set, where a coin flip gets 50%. It actually beats 500 steps of Adam (55%), but this small network is slow to train, and after 5,000 steps Adam reaches 74%. Fable's run was also very expensive, at $8.08 for 17 steps.

With this new perspective on how Weight-Space Programming builds an image classification model by hand-crafting it using known pre-deep-learning techniques, let's look at the Go network Astra built in the original article and see if there are any parallels.

In the original article, Astra was given a 9x9 Go network with 1.5M parameters, all set to zero. It had a Python sandbox, but wasn't allowed to train, fit or search, and was told to make the network play Go as well as it could. In most runs, it could also use "passes": each pass plays a batch of up to 128 practice games and shows it the results. The authors ran it four times, with budgets of 0, 10, 25 and 50 passes.

Sources indicate that and that seemed to work really well. With 50 passes, the Astra-built network beat two small networks trained with reinforcement learning (PPO) in over 80% of games, and beat one of the same size, trained on 20.5 million games, most of the time. Actually, even with no practice games played at all, Astra managed to write a network that still won over half its games against the smaller networks (Takehi et al., 2026).

Let's dig deeper into this result to try to understand what's going on.

Astra describes the final solution in its output:.

The hand-coded, symmetry-preserving policy combines approximate group-liberty propagation, captures, connected-group rescues, self-atari and eye avoidance, and ko/snapback risk suppression.

In a recent development, I must disclose here that I don't know much about Go, or how Go-winning models are built. So this section was largely put together in consultation with Opus 5.5.

According to recent reports, apparently, every item on that list is a staple of classical Go programs, including counting "liberties" to tell which groups can be captured, recognising eyes to tell which groups live, handling ko, and estimating territory with an influence function, where each stone radiates influence that fades with distance. The first Go programs were built entirely on influence functions (Bouzy and Cazenave, 2001) (Müller, 2002).

Additionally, behind those 1.48 million weights is a config of 26 hand-set numbers, compiled into the network by a design script:.

According to recent reports, the design script builds the network layer by layer, like a hand-written board analysis. It starts with layer 1, which counts each stone's liberties. Then layers 2 and 3 spread that evidence through connected stones. Next, layer 4 flags groups in atari and self-atari. After that, layer 5 scores captures and rescues. And, finally, layer 6 combines tactics with connection, territory and eyes. The 26 numbers mostly set how much each rule counts.

Its improvement from practice games was nudging those numbers by hand, and adding five newly introduced rules along the way, such as a penalty for ko repetition.

Play, diagnose, add a rule or retune one, which is basically how rule-based Go programs were built for decades (Müller, 2002), and shares a lot of parallels with the image classification approach described in the first section.

Industry observers note that so the paper's most impressive from-scratch network is a rule-based Go program, compiled into weights. That is truly an incredible feat of engineering: a hand-written program that beats a PPO network trained on 20.5 million games.

In a recent development, in this article, we've taken a closer look at how weight-space programming "writes" networks, leaving aside its other findings about reading and editing weights. On MNIST and in Go, the models drew on their extensive knowledge of classical techniques and combined them in sophisticated ways, guided by careful measurement of the feedback they were given. On harder problems like cats vs dogs, though, the limits of hand-crafted features start to show.

Industry observers note that so, from these experiments at least, LLMs aren't so much "writing in weight-space" as brilliantly chaining together hand-designed techniques. And I think there's a second takeaway: there's a lot to learn from watching LLMs work. They were trained on human knowledge, and now, it seems, they have a lot to teach us.
