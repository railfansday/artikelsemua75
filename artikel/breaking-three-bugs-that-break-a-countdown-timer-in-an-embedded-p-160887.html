Breaking: Three bugs that break a countdown timer in an embedded page

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Recent findings suggest that I built a ten minute "start now" timer as an embeddable page and shipped two versions. The first one looked fine and was wrong in three ways that only showed up when someone refreshed it. If you are shipping any countdown inside a sandboxed iframe or a locked-down webview, you will hit all three.

Wrong twice. setInterval does not fire every 1000ms, and browsers throttle hidden tabs so a "one second" tick can become a minute. Then a reload wipes left and the timer starts over, which is worse than no timer.

Fix: store the moment it ends, not the number of seconds left.

Four ticks a second is cheap, and the first render is correct instead of off by a frame. If your render is heavier than a couple of DOM writes, keep the 250ms tick and only repaint when the displayed second changes.

A timestamp in the fragment round-trips through refreshes, shares, and back/forward navigation, and needs no storage.

Sources indicate that if your page runs in an iframe with sandbox="allow-scripts" and no allow-same-origin, the document has an opaque origin and touching localStorage throws a SecurityError. It does not return null. And if (window.localStorage) can throw too, depending on the browser, so the feature check itself becomes the bug.

If store is null, say so in the UI: "this tab has to stay open, a refresh starts over." I shipped a timer that silently lost its state on refresh before I wrote that sentence. The sentence costs less than the bug. (Related: Sentence Transformers in the Hugging Face Hub...)
