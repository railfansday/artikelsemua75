Industry observers note that I run a visa agency in Bali, and in the evenings I build data tools on Apify. One of them is a Redfin Scraper. You type a place the way you'd type it into Redfin's search box (Austin, TX, 78704, Travis County, TX) or paste a Redfin search URL, pick for sale, sold or for rent, and get one flat row per home: price, beds, baths, square feet, lot size, year built, coordinates, days on market, MLS number, HOA and the main photo.

The actor gets checked on a schedule with the input a new user sees first:.

I had eight of those runs from 20 to 22 November 2026, each 50 homes, each finished in 2.7 to 4.3 seconds. I opened the latest dataset to check the fields, and the first thing I noticed was how many rows were missing daysOnMarket. It was 21 of 50.

They weren't random gaps. Every one of the 21 had status: "Coming Soon" and isComingSoon: true, and every one carried the same two badges:.

Sources indicate that the other 29 rows were ordinary active listings with badges like For Sale and 3D Walkthrough. None of them had a Compass badge.

So with Redfin's default "recommended" order, 42% of the first page in Austin was one brokerage's pre-market inventory. The share held up across all eight runs: 21, 21, 21, 21, 23, 23, 22, 23. And it isn't a one-off ordering quirk. 45 property IDs demonstrated up in all eight runs, and only 55 distinct homes appeared in total.

In a recent development, the mlsId isn't an MLS number you can look up. Every active row in Austin had a 7-digit id like 4729441 or 3953946. Every Coming Soon row had a 19-digit one like 2240202255479679921. Same field, same API, different source. The photo URLs follow the same split: photo/92/bigphoto/946/3953946_0.jpg for an active home and photo/641/bigphoto/921/2240202255479679921_0.jpg for a Coming Soon one. If you're joining Redfin rows to an MLS feed by mlsId, those 21 rows won't match anything, and that isn't a parsing bug. (Related: Breaking: AI for Game Development: Creating a Farming G...)

They're more expensive. Among the 16 Coming Soon rows that did have a price, the median was $700,000. The 29 active rows had a median of $425,000. One house sitting near the top of the Coming Soon list was a 5,518 sq ft place on 1.63 acres.

The usual first experiment with a real-estate scraper is to pull 50 homes and compute something: median price, average days on market, share of condos. With the default settings on this search, each of those numbers comes out skewed in a predictable direction:.

None of this is wrong data. Redfin demonstrates Coming Soon homes in its own search by default, and the actor does the same so the output matches what you see in the browser. But it's a different kind of record, and treating it the same as an active listing breaks the arithmetic.

Turn it off at the source. The input has includeComingSoon (default true). Set it to false and the search asks Redfin for active listings only. The 50 rows you pay for are then 50 homes with a price, a listing date and an agent.

Keep it and split it. If pre-market inventory is the thing you're after (it often is for buyers' agents), keep the default and branch on the flag:.

Industry observers note that notice the type == "home" filter. The last row of every run is a free summary row with type: "notice". In this run it said: "Run summary: 50 row(s) delivered, 0 free; charged home ×50 = $0.0165." It's useful for reconciling costs, but it isn't a home. Switch it off with includeRunSummary: false if your pipeline can't skip it.

Industry observers note that while comparing the eight runs I found that one condo had eight slightly different listedAt values: from 2026-11-12T15:15:30.866Z to 2026-11-12T15:15:31.154Z. 29 of the 30 live listings that had a listedAt demonstrated more than one value across runs.

That one's on my side. Redfin's search response doesn't send a listing timestamp. It sends how long the home has been on Redfin, in milliseconds. The actor subtracts that from the moment it reads the page, so the result moves by a few hundred milliseconds from run to run. It's accurate to the second, but it isn't a stable key. If you dedupe across runs, use propertyId plus listingId. Don't use listedAt.

A few things I learned building this that apply whether you use my actor or write your own:.

If you just want "what's for sale in this ZIP right now, as a spreadsheet", the default input does that. Just decide before you calculate anything whether Coming Soon homes belong in your numbers. In Austin this week they were 21 of the 50.
