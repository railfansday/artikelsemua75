he second-most-common reason I reach for Redis is a job queue.

Not a high-throughput event bus — just "send this email", "sync this customer", "generate this PDF". A few hundred jobs a day on a single VM. And yet the default advice is to add BullMQ or Sidekiq, which means adding Redis, which means another process to monitor, another persistence model to reason about, and another backup job nobody wrote.

There is a middle path that fits the same small deployment as the app: keep the jobs in the same database as the data, and make the queue semantics explicit with a single atomic operation.

According to recent reports, the database is NonoDB, a single Rust daemon over LMDB. The same pattern works against any document store with an atomic find-and-upgrade, but NonoDB's find_and_modify makes the claim a one-liner. (Related: Google Home speakers get a major Gemini upgrade ‘soon,’...)

Everything is a document in the _jobs collection. There is no hidden queue state.

It has been revealed that status is one of pending, running, done, failed. due_at is a Unix timestamp in milliseconds; a job is claimable when status == "pending" and due_at <= now. A claim adds lease_id, lease_until, worker_id, and started_at.

According to recent reports, A lease without fencing is a bug waiting for a slow handler. Suppose worker A claims a job with a 60-second lease, then pauses for 90 seconds — GC, a slow HTTP call, a container freeze. Worker B recovers the expired lease and starts the same job. Now A wakes up and writes "done".

The job runs twice and the bookkeeping lies about who finished it. That is why every claim writes a fresh lease_id and every completion filters on it:.

If worker B recovered the lease, it overwrote lease_id. Worker A's update matches zero documents and returns False. A can log "lost lease, discard result" and move on. The unique fence per claim is what makes the lease safe, not the timestamp.

Use find_and_modify with remove=True instead of an patch when the job document should disappear on success.

A failed handler should not spin. Return the job to pending with a growing due_at, up to max_attempts:.

Again, the filter includes lease_id. A worker that lost its lease cannot mark someone else's job as failed.

It has been revealed that crashed workers leave jobs stuck in running. A periodic sweep moves them back to pending:.

update(multi=True) is one transaction, so the sweep cannot interleave with a claim that is already in flight. Run it at worker startup and every 30 seconds while running.

Sources indicate that does the recovered job double-run? It may, if the original worker is still alive. That is exactly why handlers must be idempotent. The fence protects the queue state; it cannot un-send an email. At-least-once is the honest contract.

It has been revealed that --once claims and runs at most one job, which is handy for a systemd timer if the jobs are infrequent. A long-running worker with a one-second poll is the low-latency option. The queue semantics are the same either way.

If you already run Redis for caching, adding BullMQ is cheap. If you need hundreds of thousands of jobs per second, per-job priorities with fair scheduling, or cross-region workers, use a system built for that.

But if the real requirement is "a few durable background tasks on the same box as the app", a collection with two indexes and one atomic operation is a lot less infrastructure than a message broker.
