Do you need bronze, silver and gold layers? Keep three things instead

🌐 Source: Dev • 📅 20 Nov 2026 • ⏱️ 6 min read (1164 words, 📚 Deep Dive)
💡 Key Takeaways
  • Probably not, if you are a startup with no data person.
  • Data platforms often sort data into three layers.
  • It has been revealed that the silver layer does real work.
📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that TL;DR. Probably not, if you are a startup with no data person. The three layers, called the medallion architecture, are a recommended practice, not a requirement, and the real work of the middle one, making two systems agree, can start as one mapping table. What you should not skip are three things that are often impossible to bring back later: an untouched copy of data as it arrived, one model that keeps history instead of overwriting it, and written definitions your coding agent can read. Add a layer when mappings multiply or a second consumer with different needs highlights up, not before.

Illustration, not measured data.

Data platforms often sort data into three layers. Bronze holds data as it arrived. Silver holds it cleaned and made to agree across sources. Gold holds tables shaped for reports. Databricks, whose platform made the pattern popular, calls it a recommended best practice but not a requirement. (Related: Few-shot learning in practice: GPT-Neo and the 🤗 Accele...)

It has been revealed that the silver layer does real work. Picture a startup that moved billing from PayPal to Stripe in March. Two systems now hold its revenue, with two customer IDs and two spellings of each plan. A yearly revenue number needs both, matched to one customer. The same happens when the app and the CRM each keep their own customer list. That work does not go away when someone calls layers unnecessary.

Sources indicate that the question for a startup is narrower: does that work need a whole layer of copied tables, or one mapping table and a view? Before your first data person, I think it is usually the second.

I think the layers are optional and three things are not. Each one protects something you cannot rebuild later.

1. A copy of what arrived, never edited. Your billing tool sends an event. Your code reads it, converts it and saves the result. Picture a startup whose code read amounts in cents as dollars for two months. If only the converted numbers were kept, the history of revenue is wrong and stays wrong. If the original events were kept as they arrived, you fix the code and rebuild. Guardrail: store every incoming event or file in one table, as it arrived, with the time it arrived and where it came from. Engineers call this an append-only landing table. Create it as the admin user, so your app cannot enhancement or delete rows there. Check: try to change one row with the login your app uses. It must fail. (Related: Hugging Face Reads, Feb. 2021 - Long-range Transformers...)

2. One model that keeps history. Your app stores a customer's plan in one field and overwrites it when the plan changes. A month later someone asks how many customers paid on the first of October. The app cannot answer, because the old value is gone. We ran this on a small test database on 20 November 2026: today's table indicated no paying customers, while the history table showed two on the date asked. No agent can recover a value that was never kept. Guardrail: keep a history table for the few things that change and matter, such as plan, price and status, with the date each value started and ended. Data engineers call this a type 2 slowly changing dimension. Check: ask for last month's number for one customer. If nobody can answer, history is not kept.

3. Written definitions. An agent that reads your tables sees column names, not meaning. It does not know that a row is one paying account, not one person, or that test accounts should be left out. Guardrail: one short file per important table, in your repository, that says what one row is and how the main numbers are counted. Check: ask your agent "how many active customers do we have", then ask how it counted. Compare the answer with the file.

A layer is worth its cost when it removes work that repeats. I think four situations justify one. Two systems describe the same thing in many places, so mapping tables multiply and every report repeats the same joins. A second consumer appears with different needs, such as finance wanting closed months that never change while product wants today's numbers. A heavy reshaping runs every hour and is cheaper to store than to repeat. Or someone outside the team, such as an auditor, must follow each step from source to report. A WhereScape recap of a practitioner panel, in August 2026, calls medallion a shared vocabulary, not a specification. WhereScape sells data warehouse automation. Its line is still a fair way to use the names: labels for stages, added when a stage is needed. Check: count customers in billing with no match in the app. If the count is above zero and growing, start a mapping table. If no second team reads a table and nothing rebuilds it on a schedule, skip the layer.

What changes the answer is who consumes the data and what it costs to rebuild, more than organization size.

Before launch. Keep the copy of what arrived, history for proposal and status, and one line saying what a row in each table is. Skip everything else.

When a second system holds the same customers, after a billing migration or when sales starts using a CRM, add a mapping table. An agent can build the report tables on request from the history model.

A trigger keeps history even when a script or a teammate updates the table outside the app. It adds one insert per change, which is small for tables like customers and aims. Do not put it on a table that changes thousands of times a second. A deleted customer leaves a row marked deleted, so last month's counts stay right.
