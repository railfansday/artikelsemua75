Most of the effort in agent-assisted coding has moved out of the prompt box and into files that sit in the repo: a spec the agent works against, an AGENTS.md or CLAUDE.md that tells it how the project behaves, and some definition of finished that a script can check. These eight longer posts each take one piece of that. Four are about OpenSpec specifically, because it changed a lot this year. The rest cover the instruction files, the loop that runs against a spec, and what has to be true before you stop watching. Each entry has a short take and links to the English post plus a Chinese version.

OpenSpec's idea is simple: describe a change as a proposal with requirement deltas, let the agent implement against it, then archive it back into the main specs so the next change starts from what's actually true. The tutorial walks one change from init to archive with pinned versions, and spends real time on the boring problems: which openspec binary your PATH is picking up, why /opsx:propose belongs in the assistant chat rather than your shell, and what the 2.0 upgrade will overwrite. It also makes a clear case for when OpenSpec is worth it (brownfield repos that keep piling up decisions) and when it isn't (throwaway prototypes). Sources indicate that stores are OpenSpec's answer to a problem every team hits eventually: one capability spans three repositories, or a platform team owns requirements that product teams need to read but shouldn't edit. A Store is a separate OpenSpec repo registered on your machine, and normal commands can target it with --store . The guide sets up a shared contract used by two code repos, then digs into the parts that bite: references are read-only context, not write ownership, and picking the wrong root is the most common way an agent quietly writes to the wrong place. Six OpenSpec releases landed in under a month, and three of them need you to do something: a higher Node floor, skills moving into .agents/skills/, and a 2.1 default that installs skills globally instead of per project. This hands-on upgrades a real 1.15 project to 2.1.1 and records what the dry run indicates, where it refuses to switch to global (one edited command file is enough), and what happens to a teammate still on 1.x. The verdict is practical: upgrade, but keep skills in the repo for team projects until per-repo version pinning exists.

Instead of a feature grid, this comparison gives BMAD, Spec Kit, OpenSpec and PromptX the same tiny job: a normalize_name function with seven acceptance tests. The useful part is what that exposes. Decisions like "is None an error?" or "does a non-breaking space count?" belong to people, and no role name or workflow makes them for you. The recommendation follows from that: OpenSpec when behavior has to stay in maintained specs, Spec Kit when project principles need to carry through planning, PromptX when reusable role context is what's missing. Recent findings suggest that if your team uses both Codex and Claude Code, the default here is sensible: one shared AGENTS.md, plus a thin CLAUDE.md that imports it. The post is precise about the loading rules, which are less obvious than they look. Newer Claude Code can read AGENTS.md directly, but a project CLAUDE.md blocks that fallback by default, so having both files doesn't mean both load. It reveals how to check what really got into context. The second half collects patterns worth stealing, like adding a rule only after a mistake repeats and treating subagents as a way to keep the main context clean rather than as role play.

Recent findings suggest that the Ralph Wiggum loop is literally while :; do cat PROMPT.md | agent; done. Every pass starts with a fresh context, so there's no accumulated confusion, and memory lives in the file system, in git and in a guardrails file where each failure leaves a note for the next pass. This long essay argues that the loop and a structured spec are two layers of one stack rather than rival philosophies. Without a spec, the loop churns with no definition of success. Without the loop, one long conversation drifts into the part of the context window where the model gets worse. The argument is persuasive even if you skip the economics forecasts at the end.

Industry observers note that lauren Tan's talk is usually quoted for her PR count. This write-up focuses on her actual claim: throughput comes from trusting what agents return unattended, not from opening more of them. Her ranking of where a correction should live is what stayed with me. From strongest to weakest: make the bad pattern impossible in the codebase, catch it with lint or CI, and only then write a rule or skill. Rules get skipped. A lint error doesn't. It's a useful corrective if your AGENTS.md has grown into a wish list.

Recent findings suggest that A spec is only as good as the acceptance check at the end, and this survey lists seven ways an agent's "done" turns out false: tests run only in part, green results that went stale after a later edit, subagent failures that never reach the summary, tests that still pass with the change reverted, and more. It compares the fixes people use (evidence receipts, pre-done gates, Stop hooks, side-channel records) and where each one breaks. Its view on human attention fits the rest of this list well. Spend it up front on acceptance criteria and test names, and at the end on whatever the tools flag.

What ties these together: each one moves an expectation out of a chat message and into something that persists and can be checked. That might be a spec delta that gets archived, an instruction file you can confirm actually loaded, a guardrail note the next loop reads, a lint rule, or a receipt tied to a commit. The more of your intent lives in those places, the less depends on any single conversation going well.
