Every hand-built Linux image eventually grows the same wart: a shell script that pipes commands into sfdisk, calls partprobe, runs resize2fs, and hopes the device really was /dev/sda.

It works exactly once. Change the disk, add a partition, or boot the same image on a board that enumerates storage differently, and the script either fails halfway or, worse, succeeds against the wrong device. The deeper problem is that the script encodes positions. What you actually mean is "this disk should have a swap partition and a root partition that fills the rest.". Sources indicate that systemd-repart is the declarative version of that idea. You write small .conf files describing the partitions that should exist, and the tool makes the partition table match. It is incremental by design: existing partitions are matched by type, missing ones are appended, and when the table already matches the configuration it does nothing at all. It is used to build OS images, and it can run from the initrd to adapt a minimal image to whatever disk it landed on. (Related: How to Build a Healthcare Robot from Simulation to Depl...)

This is the practical guide: the mental model, three working configurations, and the failure modes that cost people data.

Start with the boundaries, because they explain most of the confusing behaviour:.

Recent findings suggest that if you need to shrink a partition, this is the wrong tool. For creating and growing partitions on an image or a fresh disk, it is the right one.

Definitions live in *.conf files read from:.

Industry observers note that files are sorted by filename, ignoring the directory prefix. That sort order is the whole configuration language for "which partition is which", so the numeric prefixes (10-, 20-, 50-) are not cosmetic.

That has a concrete consequence for A/B root setups: two files with Type=root, named 10-root-a.conf and 20-root-b.conf, will bind to the first and second root partitions respectively. Rename 20-root-b.conf to 05-root-b.conf and you have silently swapped which physical partition each definition controls.

Industry observers note that newly introduced partitions are not necessarily written in table order on disk. The allocator places each one in the smallest free area large enough to satisfy its constraints, so a late-numbered partition can end up physically before an earlier one. Partition numbers stay stable; offsets do not have to be monotonic.

Sources indicate that this is where most surprises come from. The allocator takes the free space and distributes it according to three settings:.

The default is a minimum of 10M and no maximum. That single default explains the most common question: "why did my root partition take the entire disk?" Because you said it could.

Sources indicate that there is also an automatic floor: with Format= set, the minimum is raised to the minimum size of that filesystem. ESP and XBOOTLDR partitions get bumped to 100M on 512-byte-sector images and 260M on 4K-sector images, even if you asked for less.

systemd-repart defaults to --dry-run=yes. Running it bare does not write anything; it prints what it would do. That is a good default and a terrible surprise when you think you just resized a disk.

With no positional argument, the tool operates on the block device backing the root filesystem. Inside the initrd it operates on the device backing /sysroot/ instead. --list-devices shows candidate devices, and passing - as the device makes it print the minimum image size for the configuration without touching anything.

Recent findings suggest that --pretty=yes gives you a human-readable table plus a graphic of the proposed layout. --json=short or --json=pretty gives machine-readable output, including the verity root hash when relevant.

Then apply and grow the filesystem:.

It has been revealed that growFileSystem=yes sets bit 59 of the GPT partition entry flags (the Discoverable Partitions Specification "grow file system" flag). systemd-growfs@.service and the x-systemd.growfs fstab option honour that flag, and systemd-growfs grows a mounted filesystem to the full size of its block device. On partition types that support the flag it defaults to on, so the line is documentation as much as configuration.

In a recent development, two caveats. First, a partition can only grow into free space immediately after it; if another partition sits behind it, the allocator cannot move things to help. Second, if your root filesystem lives on LVM, md RAID, or another stacked device, there is no GPT "root" partition to match. The packaged unit lists exit code 76 ("can't find the root block device") as a success for exactly this reason.

Note that Format= only applies when the partition is newly created. It has no effect on an existing partition, which is why re-running the tool is safe but also why it will never reformat something you already have.

This is the workflow that replaces image-building shell scripts. Two definitions:.

Build a minimal image file, populating the root filesystem from a staging directory:.

According to recent reports, copyFiles= takes source[:target[:options]] and implies Format= if you did not set one (vfat for ESP/XBOOTLDR, ext4 otherwise). Copying stops at filesystem limitations: symlinks, FIFOs, sockets, and device nodes are skipped on vfat with a log message, and UIDs/GIDs are preserved as-is.

Verify the result without mounting it:.

Then write it to the target medium with dd or your usual flasher, boot it, and let the on-disk configuration take over.

Partition UUIDs and the disk UUID are derived by hashing a seed, which by default is the machine ID read from --root=. Images built from the same tree therefore get the same UUIDs. Pass --seed=random when you want them randomized, or an explicit UUID when you need byte-identical rebuilds. This matters for dm-verity and for anything that pins a root hash.

Encrypt= wraps the partition in LUKS2 before Format= or CopyBlocks= runs, so the filesystem is created inside the encrypted mapping:.

It has been revealed that encrypt= accepts off, key-file, tpm2, and key-file+tpm2. The LUKS2 UUID is derived from the partition UUID, and the LUKS label defaults to the partition label prefixed with luks- (override with VolumeLabel=, systemd 259+).

One trap: with Encrypt=key-file and no --key-file=, the empty key is used. That is intentional for provisioning flows where a real passphrase is enrolled later, but it is not what you want on a finished image.

A partition marked FactoryReset=yes is deleted and recreated empty when the tool runs in factory-reset mode. That mode is triggered by --factory-reset=yes, by systemd.factory_reset=yes on the kernel command line, or by the FactoryResetRequest EFI variable. --can-factory-reset checks whether any partition is marked, exiting zero if so and non-zero otherwise, which is convenient for installer UIs.

Because it deletes data, treat this as a deliberate feature with a test proposal, not something to enable because it sounds tidy.

Run these in order the first time you use the tool on real hardware:.

Recent findings suggest that to restore the table: sudo sfdisk /dev/nvme0n1 < /root/parttable-backup.txt. This restores the partition entries, not filesystem contents, so it is a safety net for table mistakes, not a backup strategy.

In a recent development, never point --empty=force at a disk you like. It creates a fresh table unconditionally, which in practice means erasing everything.

For everything else, the payoff is real: the same configuration builds your image, adapts it on first boot, and can be re-run at any time without changing anything. That idempotence is the part shell scripts never quite deliver.
