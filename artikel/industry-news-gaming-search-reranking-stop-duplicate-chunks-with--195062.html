Short answer: when retried bulk ingestion gives the same chunks fresh IDs, derive each vector ID from the document ID plus chunk index so that repeating the write overwrites the existing record. The concrete failure mechanism is a retry or rerun that inserts the same chunks under fresh vector IDs. Random IDs turn another attempt into another record; a reranker downstream receives the records that retrieval selected, including duplicates.

Sources indicate that in a proposed diagnostic fixture, a gaming support article about reconnecting after a match disconnect parses into 3 chunks. Ingest that document twice, deliberately repeating the same operation, and inspect both the IDs and the indexed count for that document. Three records after both writes is the intended invariant. Six records with different IDs for the same three chunk positions exposes append behavior in a workflow that needed replacement. These numbers describe a test fixture, not an observed production incident or a vendor benchmark.

It has been revealed that the distinction matters for latency as well as relevance: repeated evidence in a finite candidate set leaves less room for other documents, while expanding the candidate set to compensate asks the reranking stage to process more input. That's a poor first response to an ingestion identity error. Whether a larger candidate set improves relevance enough to justify its latency belongs in a later evaluation, with clean inputs and the same query set.

Sources indicate that don't infer duplication from similar text alone. Two different support articles can legitimately discuss the same symptom. Compare document identity, chunk position, and content together; otherwise, cleanup intended to remove ingestion duplicates can erase useful independent evidence.

An aggregate success rate can stay reassuring while the index accumulates duplicate records.

The identity rule is small: a stable document ID plus the chunk index determines the vector ID. Keep the document ID stable across retries, and use an unambiguous encoding so that separators inside an ID don't accidentally create collisions.

There is a second rule that's easy to miss. Replacing positions 0 and 1 doesn't remove an old position 2. When chunk counts may change, delete the records belonging to that document before re-upserting the current chunks, then count the result. Deterministic IDs address repeated writes; document cleanup addresses obsolete positions.
