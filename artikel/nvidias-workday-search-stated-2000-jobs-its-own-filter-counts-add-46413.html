I run a visa agency in Bali and build scrapers on Apify on the side. One of them reads Workday career sites — the firm.wd5.myworkdayjobs.com pages that NVIDIA, Salesforce, Adobe and a long list of banks and retailers use to publish openings. My own reason for caring is simple: when a company starts hiring a lot in Indonesia, somebody there will soon need a work permit.

Workday is a pleasant target compared to most job boards. There is no login, no browser needed, and every tenant runs the same JSON API. But on 21 November 2026 I noticed that the number the API reports as total is not the number of jobs on the site. This post is about that, plus the other things I had to learn before the rows came out clean.

Open any Workday career page with the network tab open and you will see the page call itself:.

Sources indicate that the path is /wday/cxs///jobs. The tenant is the first label of the host (nvidia), the site is the first path segment after an optional locale like en-US. Each job in the response has an externalPath, and a GET on /wday/cxs// returns the full posting: description HTML, time type, country, additional locations, requisition id, the date it went live.

Here is what NVIDIA's endpoint answered on 21 November:.

It has been revealed that same number for "everything" and for one keyword. That alone is suspicious. The first page of the response also carries facets — the filters you see on the left of the career page — with a count for every value. Summing the jobFamilyGroup facet:.

Three independent facets agree on 2,645. For "engineer" the job-family facet summed to 2,516, against a total of 2,000.

So I paged past the ceiling to see what happens:.

No error, no empty page — past 2,000 the endpoint hands you page one again. A scraper that trusts total stops at 2,000 and misses 645 jobs. A scraper that ignores total and keeps going until the page is empty never stops, and fills your dataset with duplicates.

According to recent reports, the fix is the facets themselves. Filtering by one job family brings the count under the ceiling, and then total is honest:.

According to recent reports, that returned total: 1641 — exactly the Engineering facet count. Split by job family, page each slice, de-duplicate by externalPath, and you get the whole site.

One caution: facet sums are only a good estimate when a job can sit in one value. On Salesforce the first facet is the posting country; it summed to 1,643 while total said 1,614, because a job open in two countries counts twice. Adobe's external site was small enough that both said 253. The ceiling only bites on significant tenants.

Honest status of my own tool: today the Workday Jobs Scraper follows total and de-duplicates, so it stops cleanly at 2,000 per search — no duplicates, but also no job 2,001. Splitting by facet when total hits exactly 2,000 is the next change. If you need more than 2,000 rows from one employer before then, run several keywords: each search has its own ceiling. The last run before I wrote this was the default example: NVIDIA, keyword "engineer", 40 jobs, full postings on.

It finished in about 25 seconds, made 43 HTTP requests (two search pages, 40 postings, one for the company name) and charged $0.054. One row, trimmed:.

The median description was about 3,600 characters of plain text, with the HTML kept next to it.

postedOn is a label, not a date. The search returns "Posted Yesterday", "Posted 4 Days Ago", "Posted 30+ Days Ago". In those 40 rows, 17 mentioned "30+ Days Ago". The posting endpoint has the real startDate, and for those 17 it ranged from 20 October back to 2 March — anywhere from one month to almost nine months. If you sort by freshness using the label, a March posting and an October one are tied. Take the date from the posting call, which means paying for the second request per job. It has been revealed that there is a sharp edge here in my own Actor that I found while writing this: the "posted within N days" filter reads the label, before the posting is fetched, and treats "30+" as 30. With a window of 30 days or less that is fine — "30+" posts drop out. With a 60-day window, a job from March gets in. Until that is fixed, use 30 days or less, or filter on postedAt yourself.

Industry observers note that hiringOrganization is the legal entity, not the brand. 40 NVIDIA rows named twelve different employers: "2100 NVIDIA USA" (18), "IL00 Mellanox Technologies, Ltd." (9), "IN01 NVIDIA Graphics Bengaluru" (3), and nine more, each with an internal code in front. Nine of the 40 engineering jobs are formally Mellanox, the Israeli company NVIDIA bought years ago. For a recruiter that is noise. For someone working out which local entity will sponsor a visa, it is the most useful field in the row. The Actor keeps it as is and puts the brand from the career page's og:title in company.

According to recent reports, remoteType was empty on all 40. Twelve of those rows had "Remote" in the location itself ("US, CA, Remote", "Poland, Remote"). NVIDIA simply does not fill the remote field; it encodes remote work as a location. If you filter remote jobs by remoteType, you get zero on this tenant. Check the location strings too.

Workday sits behind Cloudflare, and its 429 is often not a rate limit but a bot challenge. On 16 November that challenge was triggered by the TLS handshake of a newer Node.js image on every route, residential proxies included; going back to Node 20 passed four requests out of four. If you write your own client and get 429 from the first request, try a different runtime before buying proxies. Workday also puts tenants into scheduled maintenance, mostly at weekends; the API then redirects to a maintenance page instead of returning JSON, and the only fix is to wait.

The dataset ends with a free type: "notice" row summarizing the run; filter on type == "job".

The first thing I would check on any Workday tenant now is whether total is exactly 2,000. If it is, the real number is in the facets.
