In an earlier devlog, we explained how we optimised the nebula of Vesper Protocol. Several readers asked us to start from the beginning. So here are the basics of volumetric raymarching, step by step, with a complete GLSL shader you can paste into Shadertoy.

A typical game engine draws triangles: it projects their vertices onto the screen and colours the pixels they cover. That works very well for a spaceship or a wall. But a nebula has no surface: it is a cloud of gas, more or less dense, that light partly passes through.

Sources indicate that raymarching flips the problem around. For each pixel, we cast a ray from the camera and walk along it in small steps. At each step we ask: "how dense is the gas here?" We accumulate what we see until we leave the volume or the gas becomes opaque.

Recent findings suggest that everything happens in a fragment shader, the program the graphics card runs for every pixel. On Shadertoy, this program is called mainImage and receives the pixel position. (Related: Animal control called to rescue alligator that turned o...)

According to recent reports, A ray is an origin (the camera, ro) and a direction (rd). We start by centring the pixel coordinates and correcting for the screen's aspect ratio:.

The point at distance t along the ray is simply ro + rd * t. Increasing the focal length narrows the field of view, like zooming in.

Industry observers note that we need a function density(p) that returns the amount of gas at point p. To get natural swirls, we use value noise: pseudo-random numbers placed on a 3D grid and smoothly interpolated. By adding several layers of ever finer noise (octaves), we get fBm (fractional Brownian motion), the basis of almost every procedural cloud. To break up the overly regular look, we distort the coordinates with a first fBm before computing a second one (domain warping): the swirls stretch like gas. We then confine this noise inside a soft sphere, otherwise it would fill all of space, and subtract a threshold to carve holes between the clouds.

Recent findings suggest that when light passes through a gas, part of it is absorbed. The Beer–Lambert law says that the fraction that gets through, the transmittance, decreases exponentially with the density crossed:.

Recent findings suggest that our nebula is also emissive: gas heated by the star glows. At each step, we add the light emitted there to the pixel colour, attenuated by all the gas already crossed (the current transmittance). This is front-to-back compositing:.

Order matters: add the light with the old transmittance, then update it.

Industry observers note that here is the whole shader, ready to paste into Shadertoy. It adds two details: a small random offset of each ray's starting point, and an early exit once the gas becomes opaque.

This shader is deliberately simple: it recomputes all the noise at every step, at full resolution. In the game, we precompute it into a 3D texture and render at half resolution. That is the topic of our devlog on optimising the nebula shader (in French), which explains how we went from 9 ms to 2.1 ms per frame.

A live WebGL preview of this exact code runs on the Flexarion devlog.

To tweak it, open a newly introduced shader on Shadertoy, replace the default code with the code from step 4, then press Alt + Enter. Try changing STEP, the emission colours or the absorption coefficient to see the effect of each parameter.
