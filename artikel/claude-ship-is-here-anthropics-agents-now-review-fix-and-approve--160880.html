Claude Ship Is Here: Anthropic's Agents Now Review, Fix, and Approve Your PRs — and the Policy File Decides What Merges

🌐 Source: Dev • 📅 24 Nov 2026 • ⏱️ 7 min read (1336 words, 📚 Deep Dive)
💡 Key Takeaways
  • It has been revealed that the pull request used to be where coding agents stopped.
  • Anthropic just shipped something aimed squarely at that loop.
  • It has been revealed that the timing is not a coincidence.
📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

It has been revealed that the pull request used to be where coding agents stopped. You could have an agent write the feature, write the tests, and open the PR — and then you were back to the old loop: wait for review, stop what you're doing, dig back into the old code, push a fix, wait for the review to run again, then go find someone to approve it.

Anthropic just shipped something aimed squarely at that loop. Claude Ship, revealed November 23 and available now in beta, takes a pull request through review, fixes, and an approval decision — with the team, not the model, deciding where it runs and which changes still need a human. It has been revealed that the timing is not a coincidence. On the Claude Code team, Claude already writes most of the code. The bottleneck moved downstream, to everything that happens after the PR opens. Ship is Anthropic's answer to that bottleneck, and it's built from three pieces that each do one job.

Sources indicate that claude Ship is not a single agent. It's three components working a PR in sequence:.

Code Review — already generally available — performs an in-depth review of a pull request against the codebase through multiple lenses. It collects findings, adversarially verifies them, categorizes them, and posts them to the PR. Each repository can pick a review depth: Quick, Standard, or Deep.

PR Steward — in beta — works to keep a PR green. It jumps in on failing CI checks, merge conflicts, and review feedback from Code Review, other review tools, or team members. Two details matter here. First, it is designed not to approve or merge pull requests — its job is fixing, not deciding. Second, after every push it comments with what it changed and how to undo it, so nothing happens silently. Developers can steer it by commenting @claude with an instruction, or tell it to step back with @claude stop.

Sources indicate that claude Approvals — also in beta — applies an approval policy the team writes as a file in the repository. If the policy allows it, Claude can approve routine changes on its own; for other scenarios it can require deeper human sign-off. Anthropic describes it as a smarter CODEOWNERS file. The decision can weigh a variety of signals, including Code Review findings or the team's own classifiers written in natural language. That last point is the one worth pausing on. A CODEOWNERS file maps paths to people. A policy file maps kinds of change to kinds of decision — and the policy itself is versioned in the repo, reviewed like code, and visible to everyone. The approval logic becomes a team artifact instead of a setting buried in a dashboard.

Anthropic's own team is the first data point, and it's worth quoting carefully: on the Claude Code team, where Claude's review is one layer of a broader process, merged PRs more than doubled from June to September while the share of PRs reverted fell by more than 40%.

That's a team-level result with a human review layer still in place, not a claim that the agent alone doubles throughput. But the direction is clear — faster review plus fewer reverts is the combination every team wants, and it's the combination most automation attempts fail to deliver together.

The dogfooding story makes the point more concretely. A product manager on the Claude Code team can now read a piece of customer feedback, talk through ideas and tradeoffs with Claude Tag, have it open a PR, and move on while Claude Ship takes it through review, fixes, and an approval decision. Recently, a customer was confused because the Analytics API documentation implied an Admin key could pull Pro and Team usage data. The PM asked Claude Tag whether a fix was in flight, it opened one, Code Review found nothing blocking, a docs reviewer signed off, Claude Approvals passed, and the fix merged that same evening.

It has been revealed that notice what happened there: the human who noticed the problem never touched the code, but a human docs reviewer still signed off. The pipeline compressed the waiting, not the judgment.

It has been revealed that for individual developers, there's a upcoming /ship command in Claude Code. When a change is ready, run /ship: Claude pushes it, opens the PR, reviews the change, and works on feedback and failing checks to help get it ready to merge. What can actually merge still depends on the developer's permissions and the repository's branch rules. The command is rolling out in Claude Code and the desktop app starting November 23.

For admins and engineering leaders, Ship can be turned on for an entire repository, and it then works across the team's pull requests automatically — no /ship invocation needed. An admin turns on Code Review and PR Steward for each repository; Claude Approvals starts when a connected repository has a policy file on its default branch, and an admin can turn it off. Admins choose the review level, when reviews run, and spend limits. It works with existing branch protection and required checks, so it slots into the pipeline rather than replacing it.

Anthropic's own rollout advice is worth following: start with one repository, pick a review level and schedule, set a monthly spend limit, and run the approval policy in observe-only mode until the team trusts it. Only then configure branch protection to require Claude Approvals' green light.

In a recent development, ship usage is billed on tokens, so turning it on can add to an organization's costs. The amount depends on the number and size of pull requests covered, the review level, how often reviews run, and how much work PR Steward does. Admins can set spend limits for Code Review and PR Steward.

Recent findings suggest that claude Approvals has no base charge, but classifiers in a policy are billed on the tokens they use — and a policy that uses Claude's review triggers a billed Code Review, even in observe mode. Running /ship counts as regular Claude Code usage.

There are also hard exclusions: Claude Ship is not available to organizations with Zero Data Retention, the HIPAA configuration, or customer-managed encryption keys. It's available on Claude Team and Enterprise plans for repositories on GitHub.

Eligible Claude Enterprise organizations can claim at least $10,000 in Claude Ship credits, to use within 30 days of claiming, with claims open until January 15, 2027.

The real shift here isn't that an agent reviews code — plenty of tools do that. It's that review, fixing, and approval become one continuous pipeline owned by a policy the team writes, instead of three separate queues owned by three separate humans' calendars.

Three things to watch as teams adopt it:.

Industry observers note that observe mode first, always. The approval policy is the new control plane. A policy that auto-approves too broadly is worse than no automation, because it fails silently. Running in observe mode until the decisions look right is the cheapest insurance available.

The review is a layer, not a replacement. Anthropic's own numbers come from a team where Claude's review sits inside a broader process with human reviewers. And the product itself carries the honest caveat: it uses AI and may miss bugs, security vulnerabilities, or other challenges. Treat the findings as a strong first pass, not a verdict.

Sources indicate that cost follows coverage. Token billing means the price of Ship scales with how much code flows through it. Spend limits per repository are the guardrail — set them before turning it on repo-wide, not after the first invoice.

If your team already writes code with agents, the PR queue is probably your slowest step now. Claude Ship is the first serious attempt to close that gap end to end — and the policy-file design means the team, not the vendor, decides what "ready to merge" means.
