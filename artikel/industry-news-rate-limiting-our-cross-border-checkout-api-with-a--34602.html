Industry News: Rate-Limiting Our Cross-Border Checkout API With a Token Bucket

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Industry observers note that black Friday taught us an expensive lesson. Our checkout endpoint, which normally hums along, got hammered by a mix of real buyers and retry scripts. Some of those retries were our own fault — a client that re-posted on a timeout — and each one triggered a fresh round of inventory checks and payment intent calls. We needed a limiter that could tell a burst from an abuse. Taocarts is the platform behind this checkout, and this is how we tuned its front door.

Sources indicate that our first attempt was the obvious one: a fixed counter per user, reset every minute. It was easy, and it was wrong in two ways. (Related: This 5-Minute Habit Can Calm Your Mind, Spark Curiosity...)

First, fixed windows have an edge problem. A client can send N requests at the end of one window and N more at the start of the next — 2N in a few seconds, right at the boundary. Second, a hard cap of N per minute punishes legitimate bursts. A buyer refreshing the page a dozen times while comparing shipping options is not an attacker.

What we wanted was: allow short bursts, but keep the average rate under control. That is exactly what a token bucket gives you.

Recent findings suggest that picture a bucket per key (we use tenant id plus endpoint). The bucket holds tokens, up to a capacity C. Every request consumes one token. Tokens refill continuously at rate R per second.

Two parameters do all the work: capacity C controls how major a burst we tolerate; refill rate R controls the long-term average.

We run Redis, so the bucket lives there. The clever part is that we do not run a background timer to refill tokens. We compute lazily: when a request arrives, we work out how many tokens would have accrued since the last request, based on elapsed time.

In a recent development, this is lazy refill: no cron, no per-bucket thread. The bucket only "exists" when someone touches it, and stale buckets cost nothing beyond a hash key that we let expire via TTL. (Related: How To Instantly Read Someone’s Personality With One Qu...)

Sources indicate that the naive version above has a race. Two concurrent requests can both read the same token count and both decide they are allowed. Under load, that doubles your effective rate.

Sources indicate that we fixed it with a Lua script executed inside Redis. Reading the hash, computing refill, decrementing, and writing back all happen in one atomic operation on the Redis single thread. No locks on the application side, no distributed coordination — just one script that runs to completion.

Sources indicate that this was not optional. Under normal traffic the race is rare; under a flash sale it is constant. A limiter that leaks under the exact load it is meant to handle is worse than no limiter, because you trust it.

Recent findings suggest that we set capacity to 20 and refill to 0.5 tokens per second — roughly 30 requests per minute sustained, with room for a 20-request burst. Before the limiter, a single misbehaving client could push several hundred checkout calls a minute and drag down response latency for everyone. After, checkout p99 latency stayed flat during the sale, and the number of duplicate payment intents dropped sharply.

Recent findings suggest that we also return Retry-After on rejection, computed from how long until the next token is available. Well-behaved clients back off politely instead of hammering harder.

Sources indicate that rate limiting is not glamorous work, but it is the kind of unglamorous plumbing that decides whether checkout survives its busiest hour. We would rather spend an afternoon on a token bucket than an all-nighter on incident calls.
