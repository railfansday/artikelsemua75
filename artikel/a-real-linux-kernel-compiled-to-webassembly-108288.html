A real Linux kernel, compiled to WebAssembly. It boots to a shell in less than a second.

Try it · Performance · Features · CLI · How it works · Benchmarks · JavaScript SDK.

Recent findings suggest that unkernel is Linux 7.x built as a single wasm module with a real MMU. The kernel (syscalls, scheduler, memory management, ext4, TCP/IP) is compiled code, not emulated, so programs get Linux's own behavior down to the edge cases. Only user programs are emulated: unmodified aarch64 (arm64) Linux binaries, so Alpine and Debian packages run as they are.

Open a page and you have a Linux machine with a shell, a package manager, a persistent disk, internet access, and a screen with sound. It runs entirely on your device, with nothing to install and no server, and every layer is open source. How it works explains the design. In a recent development, the syscall and fork numbers were measured on 2026-11-14 (with the riscv64 user space the project started with; the path through the kernel is the same), the JIT numbers on 2026-11-18. CPU-heavy programs are well behind native: apk search over the main index takes about 0.8 s, apk add python3 about 3.4 s. Benchmarks has the full numbers.

Anything a program relies on, from /proc and epoll to cgroups and overlayfs, behaves as it does on a server, because it runs the same code.

unkernel keeps the best of each: the real Linux kernel, running at native wasm speed, under unmodified binaries with a real MMU.

Recent findings suggest that the kernel is compiled straight to WebAssembly. User programs run on kwemu, an aarch64 CPU written in Zig and linked into the kernel. kwemu walks the kernel's own page tables, so memory management is done by the real Linux code.

When a program makes a syscall, kwemu returns to the kernel, which handles it as native wasm. There is no emulated trap and no emulated kernel mode in between. Task switches use JSPI (WebAssembly.Suspending), so the kernel gets real stacks that it can suspend and resume.

It has been revealed that kwemu runs blocks of guest code decoded once into compact ops (what has no op runs through a reference interpreter), and hot user code goes through a second tier: a JIT that compiles those blocks to wasm modules at run time, with output that matches the interpreter bit for bit. Benchmarks highlights what each tier costs.

Devices are small paravirtual drivers that talk to the JavaScript host: block (kwblk), network (kwnet, with a user-mode TCP/IP stack in JS), display, input and sound (kwfb, kwinput, kwsnd), vsock (kwvsock) and shared memory (kwshm).

Pure computation is slower. kwemu's decoded-op interpreter runs integer code at about 250-300 million guest instructions per second under Node (2026-11-17), and the JIT makes real Alpine work 1.6 to 2.3 times as fast as that (2026-11-18: an ash loop 2.5 s against 4.0 s, seq 100000 | sort -r 3.1 s against 7.1 s, seq 250000 | gzip | gunzip 3.5 s against 6.5 s), which is still well behind native.

Importing unkernel picks the Node or browser entry automatically, and unkernel/node or unkernel/web selects one explicitly. The kernel ships in the package (unkernel/unkernel.wasm) and loads from next to the entry, streamed and compiled while it downloads. It carries a small base system that mounts a distro image read-only under an overlay root and runs its init; createKernel() without distro boots the base shell (busybox and unkernel's tools), which needs no download.

The distro images are not in the package. On Node, fetchDistro("alpine") (or "debian") downloads one once from the GitHub release of the package's version, checks it against the release's distros.json (size and SHA-256), keeps it in ~/.cache/unkernel (UNKERNEL_CACHE_DIR) and returns its path; nothing else in the SDK downloads anything. In the browser, host the image yourself (it is read lazily with range requests) and pass its URL:.

Changes to the root file system stay in memory, unless a persistent data disk (labelled kwdata) is attached: then each distro keeps them in /data/distros// on it.

Networking is off unless you pass net. Any object with connect and lookup methods can carry the guest's TCP and DNS, so you can write your own backend.

createImageFromKwsparse(file, template) makes a upcoming data disk from the template the kernel carries (bundledBoot(module).datadisk). In the browser, openHttpDisk(url) keeps your writes in IndexedDB and openDataDisk() gives you the persistent data disk that the page uses. Anything that implements BlockDevice works too, and a disk of your own can be the root: cmdline: "console=hvc0 root=/dev/wda rw" with initrd: null.

exec() runs a program on pipes and resolves with { stdout, stderr, exitCode, signal }, also for a non-zero exit. Pass encoding: "buffer" for bytes, and cwd or env as you would to child_process. On the distro images programs run as the user user (uid 1000, in /home/user), who has sudo without a password; pass user: "root" (or another name or uid) to run as someone else. The base shell is root's.

spawn(file, args, { cols, rows }) runs a program on a pty, in the zigpty / node-pty shape, with resize(), kill(signal) and close() (a hangup). Run as many as you like. Keep reading output: the guest program waits while nobody does.

With pty: false the program gets pipes: stdin, stdout and stderr web streams, byte for byte.

In a recent development, A file system is a plain object tree (a function is a computed file, evaluated once per open), a MemoryFs you read and write from the host, nodeFs(dir), or your own Fs: getattr, readdir and open by path, sync or async, plus whichever change methods you want. Mounts are served over 9p on vsock. Each guest write reaches the host as it happens, and a host change demonstrates in the guest within a second.

These are byte streams with real flow control and no network in between. vsock is on unless you pass vsock: false.

Industry observers note that vm.connect(port) reaches a TCP server on the guest's loopback through the guest's kwtty, over vsock, so it needs no network. It resolves once the guest has connected (PtyError ECONNREFUSED if nothing listens) with readable and writable byte streams, half-close included, close() and closed. The CLI's --forward HOSTPORT:GUESTPORT uses it.

vm.fetch(url, init) sends an HTTP/1.1 request to a server in the guest and returns a Response whose body streams. It always connects to the guest's 127.0.0.1 at the URL's port; the host name only goes into the Host header, so vm.fetch("http://localhost:8000/") reaches a dev server listening on port 8000. fetchOver(connect, url, init) is the same client over any byte stream.

/dev/shm exists once the guest's init has mounted it, so wait for the guest before create() (an exec() waits for it). openId(id) opens a memfd that a guest program exported through /dev/kwshm. views() exists only when the kernel runs inline.

In a recent development, evdev also has button(), move(), moveTo() and wheel() for a mouse or tablet. onInput tells you when a program opens the keyboard and mouse; until then, send keys to the console. readFrame() waits for a fresh frame.

According to recent reports, the kernel runs in a worker thread or Web Worker, with the same API. Disks and the network are given as specs, which the worker builds: { kind: "file", path } on Node, { kind: "http", url } and { kind: "data", template: "bundled" } in browsers. Input and frames go through shared memory when it is available (vm.transport says). This mode is experimental.

It has been revealed that an SMP kernel (a bundle with the SMP patch) boots on several CPUs with cpus: 4, each CPU in a thread of its own on one shared memory. In browsers that needs a cross-origin isolated page and worker: true, because a CPU blocks while it waits for another, which a page's main thread may not; webCpuBlocker() notes why it cannot, and vm.stats().cpus how many CPUs the kernel got.

In a recent development, on a server, worker: true keeps the event loop free at no cost in speed, and cpus: 4 gets most of what more CPUs give (about 3x on parallel work; 8 or 16 add little, and each CPU adds to boot time and takes 9 MiB of guest memory). node test/profile.ts measures your host, and the page's /profile.html a browser.

Recent findings suggest that the SDK has some limits, on top of the kernel's known limits. There is no guest agent beyond terminal sessions, so you drive the guest through a terminal or its console, or over vsock with your own program. stop() doesn't shut the guest down cleanly, so prefer poweroff. Only one kernel can run per thread. Types ship as .d.mts and use the DOM's WebAssembly types, so a Node-only TypeScript project needs "lib": ["dom"] or skipLibCheck.

According to recent reports, you need Linux (x86-64 or arm64), Zig 0.16, Node 24, clang 21+ with the wasm target, and the usual build tools. ./setup.sh --check lists what's missing. The first build takes about 12 minutes, most of it spent on a patched wasm-ld, and uses 5 GiB of disk.

According to recent reports, the build makes the kernel bundle vendor/build/bundle/unkernel.wasm and the distro images vendor/build/distro/{alpine,debian}.erofs with their index distros.json; a source checkout uses those and never downloads them. guest/README.md describes the base system and how to add a distro.

kernel/README.md maps the kernel directory and its build steps. AGENTS.md and .agents/ hold the contributor notes: the kernel, its devices and the guest image, invariants, workflows, which tests to run, and the roadmap.
