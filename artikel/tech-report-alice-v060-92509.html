Announcing the release of Alice v0.6.0!

This change introduces several new features needed to build a small collection of packages from the Opam repository which I've been manually porting to Alice's package format in alice-ports. (Related: Latest Update: Porting fairseq wmt19 translation system...)

It has been revealed that alice packages may now refer to modules from the standard library which are excluded from the prelude, such as Unix and Str. A latest builtins section in Alice.kdl can be used to list the built-in modules a package can access:.

Packages may include C source files in their src directory. All C files will be compiled and linked into the resulting executable when building a project. The ability to compile C code raises the question of how to pass custom linker arguments to the C compiler, and this is addressed with another newly introduced feature: config scripts. (Related: Simple considerations for simple people building fancy ...)

A package may include a config script in a file named config.ml file in the package's root directory (next to Alice.kdl). The config.ml file is compiled and executed as the first step of building a package, and any lines in its standard output beginning with alice: are interpreted by Alice as directives that can influence the build. Currently the only supported directives are alice:print_endline which prints a message, and alice:add_c_linker_args which adds C linker arguments.

Config scripts can depend on other packages, and also access built-in modules from the standard library. This can be configured in Alice.kdl:.

Recent findings suggest that config scripts are expected to be run only once each time they are compiled because their output can be trivially cached in the build directory. For this reason it's faster to compile config scripts with the bytecode compiler rather than the native compiler, and of course this means compiling all their dependencies with the bytecode compiler too.

This was a necessary feature for allowing config scripts to be built with the bytecode compiler, but it might also be something people find useful to integrate into their workflow, since the bytecode compiler backend is generally faster than the native backend (but of course the executables it produces are generally slower to run).

Commands that compile code (e.g. alice build, alice run) now take a --backend argument which can be passed native or bytecode. The default is native.
