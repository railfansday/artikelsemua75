Ethereum developers want to change the gas accounting for validator deposits. The strategy is to measure the request bytes that these deposit events create.

Sources indicate that the gas calculation already accounts for executing a deposit. However, after the deposit is finished, a 192-byte request is passed along with the block. Those 192 bytes are excluded from the minimum gas charge, so the same gas limit might allow more data than the initial calculation accounts for.

Under Gloas, there is no fixed cap on the number of deposit requests per block. The execution layer has not capped this either. Gas is the only limiting factor.

Neither EIP-8131 nor EIP-8279 accounts for those request bytes. This means that deposits could become another way to bypass the gas floor once EIP-8279 closes the loophole involving cold storage reads.

It has been revealed that A relay contract can call the deposit contract repeatedly, costing around 26,000 gas per deposit. In the author's example, that execution cost is below the point where the gas floor for zero-byte calldata would start to increase the total charge.

This results in a payload of about 1.44 times the block gas limit divided by 64, compared with about 1.15 times the same baseline.

The main concern is the data size, so the proposal directly addresses the data.

A log from the deposit contract with the deposit event topic counts as 192 bytes before the log entry is added. This is the same condition EIP-6110 uses to turn logs into requests.

The cost of this would be another check that client developers would have to implement and test.

Owners are not expected to pay more for regular deposits. The cost of executing a regular deposit is already above the proposed minimum, so the extra 12,288 gas only raises the minimum charge.

The proposal has yet to be scheduled for a network upgrade.
