When AI Finds Data It Shouldn’t: Why Relevance Isn't Permission

Vibhor Kumar is a technology executive and author focused on enterprise data and AI platforms, modern architecture, and technology strategy.

​In one enterprise search project I advised on at a large financial services organization, data from a governed operational system was copied into a separate search layer to improve retrieval speed. The source system had established access rules. The search copy did not carry them all forward. (Related: Gift Tax Rules: How Much Can You Give Tax-Free?...)

Sources indicate that we discovered this when an analyst searched for information and received a client record that the original application would not have allowed that person to see. The search system had not been compromised. It was doing exactly what it had been built to do: finding information in the data available to it.

Sources indicate that even though the information was visible only internally, a user being able to retrieve a client record they were not entitled to see was a serious access-control matter. In a financial services environment, that could become an audit, privacy or compliance problem. What concerned me most was that the system looked healthy technically. There was no failed authentication or obvious security event to alert us. The weakness was in the difference between the controls on the original data and the controls on the copy. (Related: Primary vs Contingent Beneficiary: What's the Diff...)

We had moved the data without fully moving the authorization that belonged with it. I have thought about that incident again as enterprises connect more of their data to AI systems, and it shaped three practices I now recommend.

A lot of the discussion about AI data risk starts with the model: whether it could memorize sensitive information, expose something through a prompt or be tricked into returning data someone should not see. Those are valid concerns. But there is another problem that happens earlier. The AI may not need to get around a security control at all. We may already have put the data somewhere it can reach.

Sources indicate that data gets copied into vector stores, search indexes, analytical systems and training datasets, usually for understandable reasons. The source database may have years of work behind its access model: roles, tenant boundaries, retention policies, audit history and application-specific authorization. But the new retrieval layer may reproduce only part of that logic. Authentication does not fix that problem. The system still has to determine whether that user is allowed to retrieve this particular information, in this context, at this time.

The immediate fix in that project was to stop relying on the search copy as if it carried the same authorization model as the source system. The team tightened the retrieval path so that access was checked against the user’s actual permissions before a record became eligible to appear in search results. That experience is one reason I now use the phrase “filter first, search second.” Relevance should be evaluated only within the set of information the user is entitled to retrieve.

According to recent reports, semantic search is very good at answering, “What information is most related to this request?” It should not be responsible for answering, “Is this user allowed to receive it?” Before records become eligible for retrieval, the system needs deterministic controls around tenant, role, geography, entitlement or data sensitivity. If the system retrieves broadly and tries to apply authorization afterward, sensitive information may already have crossed the boundary you were trying to protect.

The more vital change was architectural. We stopped treating security on the source system as sufficient protection for downstream copies. Any latest search or analytical layer had to account explicitly for how source permissions would be preserved, synchronized or enforced at retrieval time.

In a recent development, that does not mean enterprises should stop copying data. Sometimes, a separate index is the right way to meet latency requirements, and analytical replicas can isolate expensive workloads from transactional systems. The distinction I care about is whether the duplication is intentional. When a team can explain why the copy exists, who owns it, who can reach it, how permissions stay aligned with the source and when the copy should disappear, the trade-off is reasonable. Problems start when the copy survives longer than the thinking that created it. At that point, it becomes architectural debt.

Deletion makes the problem tangible. If a record must be deleted, restricted or no longer made available, changing the source is not enough if the same information continues to exist in a search index, vector store, cache, analytical copy or AI dataset. Organizations need to know not only where the authoritative record lives but also where derived representations of that record exist and whether changes in permission, retention or deletion propagate to them. That is a privacy and compliance obligation as much as an architectural one.

In a recent development, A simple test: When a customer, employee or document loses access in the source system, can the organization show that the same information is no longer retrievable from every derived copy? If that answer is unclear, the access model is probably unclear, too.

If a CIO asked me where to begin, I would not start with a large governance program. I would first map where sensitive data has been copied for AI, search and analytics, and then compare those copies with the systems they came from. For each one, I would want to know who owns it, how access is enforced, how permissions change, how deletion works and whether anyone can prove that those controls are still aligned with the source.

AI is making enterprise information much easier to find. But finding the right information is only half the job. The other half is ensuring that it reaches someone who was actually allowed to receive it.​.
