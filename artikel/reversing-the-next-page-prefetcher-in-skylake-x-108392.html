It has been revealed that hardware prefetch enhancement: A next-page prefetcher (NPP) is added in Intel microarchitecture code name Ivy Bridge. The NPP is triggered by sequential accesses to cache lines approaching the page boundary, either upwards or downwards.

A recent matter of the optimization manual states that Redwood Cove includes a Last Level Cache (LLC) Page Prefetcher which is like NPP but with a slightly more sophisticated prefetch algorithm:.

According to recent reports, the LLC Page Prefetcher extends the Next-Page-Prefetcher algorithm, which detects a sequence of accesses that are about to reach the end of a page (either going up towards the next page in memory or down towards the previous page in memory) and triggers a linear prefetch to the start of the next predicted page. NPP intends to prefetch the translation of the next page and initiate prefetching of the first few cache lines from that predicted page. Hardware component that preloads data that the program might need soon. The goal is to eliminate memory stalls when the CPU actually demands the piece of data that the prefetcher could have loaded earlier. All kinds of prefetchers exist in modern CPUs. Next-Line prefetchers prefetch the immediate next cache line when the N’th cache line is accessed. Stride prefetchers (usually IP-based) track the stride of consecutive memory accesses that originate from the same instruction and if the access pattern turns out to be regular enough, it eagerly initiates the load from address that it predicted. Next-Page Prefetchers preload page table entries into the Translation Lookaside Buffer (TLB) provided software traverses memory pages in predictable manner. These by no means are the only three kind; a high-performance CPU may implement many other types of prefetchers, some of which are documented in this Intel whitepaper. Industry observers note that prefetchers that are required to act fast are logically simple and tend not to cross page boundaries because that may complicate things with, e.g. page faults and page walks on TLB misses. For example, the next-line prefetcher is supposed to fetch the next cache line if the accesses are sequential, but if the next cache line sits in a different page it may decide not to prefetch at all. Next-page prefetchers are slightly different in that regard; they prefetch the next page table entry (PTE) into the TLB. They have to work across page boundaries by design.

SKX (codename for Skylake-X) has two TLB levels: L1 and L2. Each SKX core gets a physically separate L1 data TLB (dTLB) and L1 instruction TLB (iTLB). The L2 TLB (also called Second Level TLB or STLB) is unified, i.e. both instruction and data PTEs go to the same STLB.

Both L1 and L2 TLBs are partitioned based on the page size. L1 dTLB has a total of 100 entries: 64 reserved for 4k pages, 32 for 2M or 4M pages, and 4 for 1G pages. The dTLB is 4-way set associative so each set can hold 4 page-table entries. The iTLB is also partitioned: has 128 entries for 4k pages, 16 entries for 2M or 4M pages, and none for 1G pages. The STLB has 1536 entries shared between 4k and 2M pages and an additional 16 entries for 1G huge pages. STLB is not inclusive of the L1 TLBs. That means at any given instance, a page-table entry may exist in one of the L1 TLBs, the STLB, or both.

Sources indicate that the very first question that we should ask is whether the next-page prefetcher exists in SKX at all. NPPs seem like a good idea in general; given that Intel had the silicon budget to include one in Ivy Bridge, we expect the answer to be “Yes” in SKX too. The seemingly useless zero helps ensure that loads from the mapped range execute serially. Take a closer look at how we’re using zero in the loop. Loading the next byte from the mapped range at iteration i depends on the value of zero computed at iteration i-1. Computing zero at iteration i-1 in turn depends on computing dummy at iteration i-1. We have a cyclic loop-carried dependency chain here: the load in map_base[i + zero] feeds add in dummy += .... The result of that add then feeds the and in zero = zero & .... Result of the and feeds the next load at iteration i+1. In layman terms, the loads at iteration i and iteration i+1 cannot execute together or out-of-order. This is intentional: alloweing out-of-order execution of the two loads could significantly perturb our results. We’ll see why in a moment.

The last line is a common trick to avoid the compiler throw away our computation; it’s falsely advertising that the inline asm uses the value of dummy computed in the loop and forcing the compiler to materialize dummy into a register.

In a recent development, note that for the prefetcher to trigger, load from 52nd cache line must execute before the load from 53rd cache line (unless the prefetcher is bidirectional, but we’ll get to that in a minute). In a recent development, if you’re wondering why would Intel design the prefetcher with such a thin trigger condition, you’re not alone. I had the same exact question.
