Stop Pasting Passwords Into Your AI Coding Agent

autologin-mcp is an open-source MCP server that logs your AI agent's browser tab into the app it is testing. The password stays on your machine and never reaches the model.

You ask Claude Code to test the checkout flow on staging. It opens Chrome, clicks through a few pages, and then the app reveals a login form: the session has expired.

Recent findings suggest that from there, the run goes one of two ways. The agent stops and waits for you, or it asks you for the password. Neither is what you wanted from an autonomous test run.

The obvious fixes all put the password somewhere it does not belong.

I wanted the agent to get past the login screen on its own, without the password ever entering the conversation. So I built autologin-mcp.

It has been revealed that autologin-mcp is a small Model Context Protocol server with one job. When the tab under test shows a login form, a "session expired" message, a 401/403 or a redirect to a login page, the agent calls its login tool. The tab gets signed in with credentials stored on your machine, and the agent only sees the outcome. (Related: How to train a newly introduced language model from scr...)

In a recent development, there are two ways to fill the form. In neither does the password pass through the agent.

The only hop that carries the password is step 5, from your machine straight to the page, and only to the profile's own site. (Related: Breaking: The Age of Machine Learning As Code Has Arriv...)

In a recent development, CDP mode kicks in when Chrome remote debugging is on (chrome://inspect/#remote-debugging, Chrome 144+). autologin-mcp connects to Chrome over the DevTools Protocol, finds the tab and fills it itself. The agent runs nothing.

In both modes the filler handles React, Vue and Angular inputs, forms that render late, identifier-first pages that ask for the email and then swap in the password field, and submit buttons in many languages.

Some logins need a person: single sign-on, passkeys, captchas, or a one-time code after the password. autologin-mcp recognises them and returns needs_human with a reason (sso, passkey, captcha, mfa_required) instead of failing or retrying, and the agent hands the login to you. Those pages never receive the credentials.

Three failed logins in five minutes pause the profile until you check the credentials, so an agent stuck in a loop cannot lock your test account.

According to recent reports, the honest part: autologin-mcp prevents accidental exposure, not a deliberately hostile agent. The username and the logged-in session are visible to the agent; only the password is kept out. Use dedicated test accounts, never production credentials.

You need Node.js 22.12+, Claude Code, and a browser tool for the agent, for example Claude in Chrome.

In a recent development, then restart Claude Code and test as usual. When the app asks for a login, the agent calls login by itself.

It has been revealed that you can add as many profiles as you need, including several accounts for the same app (say admin and viewer). A profile only fills pages whose host matches its root URL, such as example.com, *.example.com or localhost:3000.

It also reaches beyond Claude Code:.

There is deliberately no --password option, because it would leave the password in your shell history and the process list.

Industry observers note that the agent's JavaScript call often never comes back. In my Chrome profile, submitting any login form made another extension take over the tab, most likely a password manager offering to save the password. Claude in Chrome then failed with "Detached while handling command", although the login had worked. So the page also reports the outcome to the server, and a login_status tool hands it to the agent.

A memoryless agent has to find its own way. I ran five fresh Claude Code sessions (Opus, Sonnet and Haiku) on tasks that never mentioned logging in. All five called login on their own. The JavaScript call failed every time; four went straight to login_status, and one re-ran the script and got the first run's outcome. That is why the server's instructions spell out the whole recovery path.

Sources indicate that "Run this script" means three different things. Claude in Chrome's javascript_tool supports top-level await but does not wait for a returned Promise. Puppeteer's page.evaluate waits for a Promise but has no top-level await, so it fails with "await is not defined". Playwright MCP wants a function. A friend hit the Puppeteer case in a real test, and that report became a release.

A good guard is annoying. The hook blocks any shell command that so much as mentions the credentials folder, including my own test commands while I was building this. That is exactly the point.

Sources indicate that autologin-mcp is free and MIT licensed. If it saves you a babysat test run, a star on GitHub helps other people find it. Concerns and pull requests are welcome, especially reports from agents other than Claude Code.
