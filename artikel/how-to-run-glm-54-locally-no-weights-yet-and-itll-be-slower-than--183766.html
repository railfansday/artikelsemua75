How to Run GLM-5.4 Locally (No Weights Yet, and It'll Be Slower Than GLM-5.3)

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

You can't run GLM-5.4 locally today. Z.ai shipped it on November 23, 2026 as its first loop transformer coding model, and the weights aren't public yet. There's no Hugging Face repo, no model card and no license file. The zai-org org page still stops at GLM-5.3.

It has been revealed that the line from the announcement that got quoted on HN is "We initiative to open-source the model weights responsibly after completing necessary safety hardening." No date is given. When the weights do land, the loop changes your hardware math in a way most "how much VRAM do I need" posts will get wrong. Below I work out a memory budget from GLM-5.3's numbers and check how far llama.cpp, vLLM, MLX and Ollama are from loading it. (Related: How to Budget for a Wedding Without Going Broke...)

Sources indicate that A normal transformer runs every layer once per token. GLM-5.4 takes a block of 28 layers from the GLM-5 base and runs that block twice per token, using the same weights both times. WCCFtech, TestingCatalog and DataCamp all describe it the same way. (Related: What I do every time I get an IRS notice...)

Recent findings suggest that it wasn't trained looped from scratch. Z.ai took the already-pretrained GLM-5 base and converted the middle layers into a loop through continued training. GLM-5's config.json has "num_hidden_layers": 78. That's why one HN commenter summed it up as "emulating a 106 layer model in a 78 layer model.".

According to DataCamp's write-up of the blog, there are two extra pieces that matter for anyone who will implement this in a runtime:.

In this release the loop count is two, every token, every time. It doesn't loop until convergence, and it doesn't vary by token difficulty. Several HN commenters had to correct each other on that. Z.ai states it will keep scaling loop depth alongside model size, so later versions may differ.

That last row is the one I have a problem with.

In a recent development, Z.ai published no benchmark scores for GLM-5.4 itself, coding or otherwise. The only numbers come from a 30B iso-parameter ablation. With "about 10% more" training compute, the looped version beat the plain one, with the biggest gains on math, science reasoning and long context, and 10-14% shorter outputs on GPQA-Diamond and MMLU-Pro. The headline claim is that the ~750B model reaches intelligence comparable to 2T-3T parameter models. According to TestingCatalog, a Z.ai team member stated 5.4 scores will come later.

For comparison, GLM-5.3's model card lists Terminal Bench 2.1 at 88.2, DeepSWE (v1.1) at 66.9 and NL2Repo at 58.0. That's the bar 5.4 has to clear, and Z.ai chose not to show whether it does.

The only third-party number I found is AICodeKing's KingBench 4, via DataCamp: 7th overall and 1st among open models. It took 431 minutes against Gemini 4 Neon's 109, burned about 1.04M tokens against roughly 70,000, and had a 1.56% tool-call failure rate (11th of 17). DataCamp notes it's one reviewer's own harness, and people on X have already questioned which reasoning effort was used. So it's good, but it thinks a lot. Z.ai itself admits to "marathon thinking" loops.

Early HN reports match that: "decent improvement on 5.3 but nothing earth shattering," "only marginally" better on one person's codebase, and one note that "it switches to Chinese at some point.".

Sources indicate that my read: shipping a new architecture on a subscription plan, with no benchmark table and no weights, is a launch built for two news cycles. Maybe the numbers are fine. But "trust us, it matches a 3T model" from a 30B ablation is not evidence.

Because the looped layers share weights, memory scales with physical parameters while compute scales with layer passes, so the two need separate estimates.

Recent findings suggest that memory: the file size should land very close to GLM-5.3's. Treat these as estimates until a GGUF exists. Unsloth's GLM-5.3 guide lists the closest numbers available:.

For datacenter hardware, vLLM's recipe indicates the FP8 GLM-5.3 checkpoint "fits on a single 8xH200 / 8xH20 node", and that reaching the full 1M context takes 8xB200 with FP8 KV cache. Add a little for GLM-5.4: the loop gates, a vision encoder, and a sliding-window KV for the second pass.

Compute: every token now goes through roughly 106 layer passes instead of 78. That works out to about 36% more work per token from the layer count alone, even though the parameter count hasn't moved. Z.ai credits fused kernels with cutting the extra memory reads and writes the loop adds. On your hardware, expect it to be slower than GLM-5.3 at the same quant.

Recent findings suggest that HN argued about whether looping helps the memory-bandwidth wall. The clearest answer came from user ac29: "Looping saves you memory capacity needs, not memory throughput needs." At batch size 1 on a Mac, you're still streaming the same expert weights, just more times.

Recent findings suggest that Z.ai has kept this promise before: GLM-5 and GLM-5.3 both ended up on Hugging Face, and as one HN commenter put it, "they usually take a few weeks to release the weights". The license has drifted, though. GLM-5 was MIT and GLM-5.3 ships under a custom glm-5.3 license, so read whatever 5.4 comes with before you build on it.
