It has been revealed that the week before an engineer leaves is always the same week. Nobody writes anything down, because the person who knows the system is busy closing tickets, and the person who will inherit it does not yet know what to ask. Then the laptop goes back to IT and the knowledge leaves with it. (Related: Latest Update: University debuts $5m smart system that ...)

Recent findings suggest that the usual fix is a documentation sprint, and the usual documentation sprint dies at the blank page. Not because anyone disagrees that a running guide should exist, but because "write the running guide" is six files of undefined structure and no team has a free afternoon for six files. What actually gets a handoff written is a skeleton: named sections, in an order, with a placeholder where the honest answer goes. (Related: Intel Diamond Rapids reveals signs of life in SC26 demo...)

Industry observers note that that is the specific thing I went looking for and the specific thing HandoffKit is — a $13 bundle of handoff document templates plus a small bash CLI that copies them into your repository. This post is what I measured in the bundle, from a clean copy, on my machine. It includes the parts that do not work, because two of the four CLI commands do not do what the README says they do, and you should know that before you spend anything. Yes, this is a product I sell, and the article says so plainly instead of pretending to be a neutral review.

Ask a team that lost someone to name what went missing and you get a list, not a document. How do you run this locally. Which service talks to which. What is the API surface. What was deprecated and why nobody deleted it. Each of those is a section, and each section is undefined until somebody defines it — which is why the handoff gets postponed indefinitely while the successor opens fifty files to reconstruct a mental model.

Industry observers note that A template does not answer those questions. What a template does is remove the blank-page cost: it tells you the ten headings a running guide needs, in the order a reader needs them, with a {{PLACEHOLDER}} sitting exactly where the departing engineer's tribal knowledge belongs. Filling a defined outline is a two-hour job. Inventing the outline is a week nobody schedules.

Six files, all Markdown or JSON. No code generation, no model calls, no network access. I counted the words and the headings in each, from a clean copy:.

It has been revealed that 05_DEPRECATION_LOG.md — 3,590 bytes, 470 words. What is dead, what replaced it, and the migration note.

Sources indicate that kit-manifest.json — 866 bytes. The field list a kit is supposed to fill: required fields like project name, engineer, last day, manager, repo URL, version; optional fields like successor, primary language, framework, deployment target, team size, on-call info.

Recent findings suggest that that is 2,787 words of structure across the five templates. The CLI itself is one bash script, 3,414 bytes, 103 lines, exposing four commands: init, generate, diff, template.

Whether 2,787 words of headings is worth $13 is a fair question and I will answer it at the end rather than pretend the answer is obvious.

I copied the bundle to an empty temp directory and ran every command from an empty project folder, so nothing I quote here depends on my own setup.

It has been revealed that six files, matching the README's claim exactly. generate does the same job into ./handoff-kit by default, and I confirmed generate -o custom-dir honours the output flag — the six files landed in custom-dir and the directory was created for me. Exit code 0 on every run.

It has been revealed that this is the part that saves real time: you can read one template, decide whether its structure fits your stack, and skip the rest. A missing template name exits 1 with a clear error, which is the correct behaviour and the only command in the kit that gives you one.

In a recent development, reading all five end to end, they are conventional and complete. 03_RUNNING_GUIDE.md contains a quick-start block with clone, install, env-var and start steps, then prerequisites, then local setup, then environment variables. 05_DEPRECATION_LOG.md is organised the way a deprecation log is actually read — symbol, date, replacement, migration note. Nothing here is exotic and nothing is blank: every heading has instructions under it telling the departing engineer what belongs there.

Three behaviours are worth your money's worth of attention.

The README's pitch is "generate a professional handoff experience in one command — no setup, no configuration." What generate does is cp the six files into your directory. It does not read kit-manifest.json, does not prompt for values, and does not substitute anything. After a clean generate, I counted the {{PLACEHOLDER}} tokens left in the output:.

Industry observers note that 281 placeholders. That is not a defect — the templates are meant to be filled by a human, and no AI writes your architecture for you. It is a naming problem: "generate" reads like a generator and behaves like an unzip. Initiative to spend the afternoon filling these in, because that is the actual work and no command in this kit will do it for you.

diff is described as "Show differences since last generation" and the README sells it as validation: "run handoffkit diff to validate all required files are present before shipping." Present-ness is all it checks. I appended 68 bytes to a generated 01_README_HANDOFF.md (4,184 → 4,252 bytes, a real content change) and ran it:.

It has been revealed that it printed the same line it printed before the edit. The check is a single -f test on one filename: if 01_README_HANDOFF.md exists anywhere in the output directory, it reports no changes. So it will tell you a file is missing, and it will never tell you a kit has drifted — which was the only reason I wanted a diff command.

Lines 8–11 of the 103-line script are a dependency check that aborts the entire CLI when node is absent:.

The script contains no invocation of node anywhere — I grepped it: zero npm calls, zero node calls, no curl, no python. It is pure bash plus mkdir, cp, ls, sed, cat. Meanwhile the README's headline feature is "Portable Single-File CLI — no npm dependencies required" and "Zero External Dependencies — works on any modern Linux, macOS, or WSL environment." Both statements are false against the shipped script: on a clean Debian container or an airgapped build box without Node, handoffkit help exits 1 before printing help. The fix is deleting nine lines; as shipped, the portability claim does not hold.

One smaller thing, since you may script against it: an unknown command prints the usage block and exits 0. handoffkit bogus-command succeeds. If you put that in a pipeline expecting a failure signal, you will not get one.

If you buy it, the first twenty minutes should go into 03_RUNNING_GUIDE.md, not 01_README_HANDOFF.md — the running guide is the file a successor opens on day one, and the README's scope fields can wait until week two. Fill the guide with the actual commands and let everything else stay a placeholder until somebody needs it; a half-filled honest template beats a fully filled speculative one. And delete the node guard before you drop the script into CI, or skip the script entirely and use the templates as files, which is how most of the value is delivered anyway.
