Tee Splits Iterator Positions, Not the Objects It Yields

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

Two consumers can advance through one source at different positions without receiving independent copies of each yielded object. That is the distinction to test before using itertools.tee to feed separate processing stages.

The fixture below logs each upstream yield. It observes how a lagging branch replays already-pulled values and how a mutable yielded object remains shared. The log measures source advancement only. It does not measure memory allocation, scheduling, or processing throughput.

The Python tee reference explains the independent iterators, auxiliary-storage caveat, original-iterator restriction, and lack of thread safety.

It has been revealed that the last test deliberately violates the documented usage rule by advancing the original iterator after creating the branches. It demonstrates why that original should no longer be used by other code. A value pulled outside the tee branches need not appear in their sequences. This is a diagnostic fixture, not a suggested processing pattern.

The mutable-object test needs a different decision. If each stage must edit a private record, make an appropriate copy at a declared boundary or design the yielded values to be immutable. Merely splitting iteration does not supply that separation. Copying nested arbitrary objects also has a contract of its own, so this article does not prescribe a universal copy operation. A large gap between branches may require substantial auxiliary storage. The small replay test highlights the dependency on already-pulled items, but gives no byte estimate and is not a memory benchmark. The exercise is single-threaded. Tee branches should not acquire a thread-safety guarantee from these results. The fixture also does not make an upstream generator repeatable, reversible, or safe to run against external side effects.
