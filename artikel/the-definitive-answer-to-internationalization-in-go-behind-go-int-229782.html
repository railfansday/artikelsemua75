Let’s look at the thinking behind the design.

Industry observers note that imagine a page with forty pieces of text to translate. Three of them are a status label, a greeting, and the number of items in a cart.

All three are strings, but each is produced differently. Ready is already written out in the translation file. Hello, Ada! needs interpolation to fill in the user’s name. And 7 items depends on the quantity to determine whether to use item or items.

Walking through how these three strings are produced shows where go-intl saves time.

Suppose an app provides English and Simplified Chinese translations. The same key gives different text in each language.

A message index has one job. Given a string key, it returns the message index. I wanted to know whether a sorted slice was worth using when the keys were short and the dictionary had only a dozen or so entries. With a larger dictionary, how much lookup time could a hash table built specifically for these keys save? I tested three implementations on the same keys, using a sorted slice, a custom hash table with linear probing, and a Go map. At 16, 1,024, and 16,384 keys, Go’s map was the fastest on successful lookups, both when looking up one key repeatedly and when cycling through different keys. That’s why go-intl kept map[string]int.

Say a dictionary contains four messages and "screen.ready" is at index 2. With a Go map, index["screen.ready"] gives us that 2 directly.

A sorted slice keeps the keys in lexical order. In this example the messages sit in the same order, so a key’s position in the slice is also its message index.

It has been revealed that binary search compares the middle key and uses that ordering to narrow the range. For instance, "screen.copy" sorts before "screen.ready", so we can discard it and everything to its left. The first key equal to the target is keys[2].

Most of the changes described above happen before the map lookup or after the message has been retrieved.

As soon as the translation file is loaded, we know which text is literal, where the arguments go, and where each branch ends. We can keep all of that. Once a request has a language, the forty strings on the page can share it, too.

What has to wait until display time is the user’s name, how many items are in the cart, and how the number should appear.

That leaves each message with just the steps it needs at display time. For Ready, return the stored text. For Hello, Ada!, look up the name and concatenate the pieces. For 7 items, choose the wording based on the quantity, then write the number.
