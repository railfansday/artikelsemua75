When Firebase Fights Back: Debugging App Check, Google Cloud, and a Broken Deploy

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

According to recent reports, I spent a good chunk of time this week working through a build that looked fine on paper but kept throwing 401s in production. The stack was Firebase AI Logic, App Check with reCAPTCHA v3, and Vercel. The error was clear. The fix was not.

Here’s what the process actually looked like.

The build was passing. The app was still broken.

Recent findings suggest that first issue: a Rollup parse error on deploy. The reCAPTCHA site key wasn’t wrapped correctly in the provider config — Vite couldn’t parse it. Fixing that got the build green. But the 401s kept coming on the AI endpoint. (Related: Deploy Hugging Face models easily with Amazon SageMaker...)

The real problem was hiding in plain sight.

Recent findings suggest that A debug token that was fine for local development was still active in the production build. Firebase App Check saw it and tried to use it instead of the reCAPTCHA provider. The Firebase AI Logic endpoint rejected it. One line removed, redeployed, and the connection to Firebase came back.

While this was happening, the Cloud Console was showing 100% error rates across the APIs tied to this project. That’s a useful signal — not a panic button, but a clear indicator that something upstream was rejecting requests before they even got processed. (Related: My Journey to a serverless transformers pipeline on Goo...)

Working directly in VS Code, pushing commits manually, reading build logs line by line — it slows you down in a good way. You see exactly what changed and why. That’s how you learn the stack, not just the tool.

Recent findings suggest that debugging isn’t just fixing errors. It’s building a mental map of how the pieces talk to each other. Firebase, App Check, Vercel, Google Cloud — each one has its own layer. When something breaks, the error usually lives at the boundary between two of them.
