Security tends to get cast as the blocker, the people who ask awkward questions about risk or about what happens when an agent hallucinates during a critical incident. But many security people want AI. In security operations, it can take over the tedious work that burns analysts out. It can triage alerts, investigate incidents, summarize cases in plain language and isolate a host at a speed and volume no human team can match. (Related: Is Social Security Taxable? In a recent development, and we need that speed. Attackers don’t have to sit through governance reviews, and the fear of breaking things doesn’t hold them back when that’s their main aim. Reconnaissance that used to take a human hours now takes an agent minutes, and an agent never gets bored or tired of probing for a way in.

So yes, enterprises need AI in security operations. Nobody serious disputes that. But we can’t just drop agents into the SOC and expect them to perform. How do we know they’ll hold up against an attack they’ve never seen?

Here’s a familiar scenario: A regional bank buys an agentic tool to investigate indicators of compromise, which behaves perfectly in the vendor demo. It takes a known ransomware hash, queries the EDR, pivots into DNS logs, isolates the beaconing host and writes a clean case summary in under two minutes. Sold.

According to recent reports, then it goes into production, and the quirks start to show: A lender the bank recently acquired still logs in local time, so the agent stitches a timeline together five hours out of order. A legacy proxy it was never given access to returns nothing, so the agent reports “no indicators found” instead of the real answer: “I couldn’t look.” The summaries read well and the tickets close, so nothing prompts anyone to look twice, even though the risk is still there.

Now introduce a threat group that highlights up with a tactic the tool has never met. The attackers call the help desk, talk their way into an MFA reset on a finance admin’s account and move through approved remote management tools into the cloud tenant. An indicator-driven agent either closes the alert as benign or maps the behavior to the nearest known group and isolates a host while the attacker keeps working through identity. And if the phishing email claims the activity is an authorized red team exercise, the agent may simply believe it.

The quirks don’t show up in the demo, because a demo only shows an agent doing the tasks it was built for, in an environment set up to cooperate. A real production environment has a complex tech stack, messy data and a threat nobody has seen before. It’s no surprise that agents that look perfect in a controlled evaluation fall apart when the environment is unfamiliar or the information incomplete, and they fall apart faster when someone is deliberately trying to trick them.

Recent findings suggest that security teams need to find the balance between measuring whether an AI system can complete a task and proving it can make the right decisions under pressure. They have to find out how an agent will handle a different environment and the most likely attack scenarios before it goes into production.

It has been revealed that the environment needs to behave like the real thing to be taken seriously, with realistic operating systems and hardware running real applications and real agents on real data. The user side needs real activity, too: people sending emails and working in business applications while admins manage the domain and change network configuration. Every event leaves a trace, so genuine machine and network logs are crucial, too. The agent has to find the real threat in the same noise that analysts wade through every day, and legitimate business activity has to be present to see whether the agent disrupts work it shouldn’t.

Industry observers note that security leaders should start by agreeing on success criteria before testing begins. Decide what counts as a pass and what counts as a fail, and include the cases that should stop a deployment outright, like unauthorized actions or missed escalations. Then set a baseline by running existing analysts and tools through the same scenarios to have something concrete to compare the agent against.

It has been revealed that next, run real attacks against the agent, emulating the tactics and techniques of actual cyber criminal groups. Because the team controls the attack, they know exactly what happened, which means it can be held up against what the agent reported and see where it got things wrong.

Score outcomes over activity, since an agent that closes a lot of tickets or finishes investigations promptly can still leave threats unresolved or need expensive human review to clean up after it. Finally, don’t treat testing as a one-time gate at deployment. Models get updated, attacker techniques shift and data changes, so an agent that performed well in month one may behave differently in month four. Rerun the same attacks against the same environment on a regular schedule to catch that drift early.

Industry observers note that security teams don’t have to be a blocker. Run agents through realistic tests, score what they actually accomplish and retest as things change, meaning teams have evidence instead of opinion. That evidence lets teams tell the business which agents are ready for more autonomy, which need limits and which aren’t ready at all.

Companies that do this will get more out of AI than the ones that skip it, because they’ll know where it can be trusted and where a person still needs to be in the loop. The question from the start still stands: How do we know an agent will hold up against an attack it has never seen? Now we can answer it.​.
