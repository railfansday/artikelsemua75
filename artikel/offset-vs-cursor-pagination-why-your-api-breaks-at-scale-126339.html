Offset vs Cursor Pagination: Why Your API Breaks at Scale

Recent findings suggest that most APIs start with offset-based pagination. It feels natural: GET /items?page=500&limit=20 is easy to understand, easy to build, and works seamlessly when your database tables contain a few thousand records.

However, once your database table grows to hundreds of thousands or millions of rows, offset pagination quietly degrades performance and causes subtle data anomalies that frustrate end customers. (Related: Chipotle is giving customers free burritos with Thanksg...)

Here is why offset pagination fails at scale and how cursor-based pagination fixes it.

To understand why offset pagination slows down, look at what the database engine does under the hood when executing an OFFSET query.

It has been revealed that when you request OFFSET 100000, the database does not magically jump to row 100,001. It must scan and sort 100,020 rows in memory or disk, throw away the first 100,000 rows, and return only the remaining 20 rows.

As the offset increases, query execution time increases linearly ($O(N)$ time complexity). What took 2 milliseconds on page 1 can take several seconds on page 5,000, consuming massive CPU and RAM resources.

Imagine a user is viewing Page 1 (items 1 through 20). While they are reading, 5 fresh records are inserted into the database. When the user navigates to Page 2 (OFFSET 20), the database fetches rows 21 through 40 based on the current state.

According to recent reports, if records are deleted instead, items get silently skipped, and the user never sees them. In high-frequency write systems like audit logs, social feeds, or IoT streams, this makes pagination unreliable.

Cursor pagination (also known as keyset pagination) changes the query strategy. Instead of telling the database "skip N rows," you pass a pointer (the "cursor") to the last item retrieved and ask for "the next N items after this specific record.".

This relies on an indexed column, such as an auto-incrementing ID or a timestamp combined with a unique identifier.

It has been revealed that because the WHERE clause leverages an index, the database jumps directly to the matching row without scanning previous records. Performance remains $O(1)$ regardless of how deep into the dataset you paginate.

Additionally, inserting or deleting items above or below the current cursor will not shift the relative position of the remaining items, keeping pagination results stable.

In practice, backend APIs typically encode cursor values into a single opaque string (often Base64) to abstract the implementation details from the client.

Understanding your data access patterns early prevents expensive database migrations and API redesigns down the road.
