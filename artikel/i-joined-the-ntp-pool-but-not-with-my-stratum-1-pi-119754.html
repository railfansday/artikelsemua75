Before I get too deep into the time-nuts rabbit hole, I figured I should share a little bit of the good time I now have in my studio, with everyone else.

Thus, I've finally joined the NTP Pool, offering one public Stratum 2 NTP time server (ntp-01.jeffgeerling.com), which gets its time from my Stratum 1 time server (time.jeffgeerling.com) in the studio.

My Time Pi is connected to an outside GNSS antenna through a TimeHAT v6, which I paired with a high quality timing-grade GNSS module, the u-blox ZED-F9T.

Right now the NTP Pool doesn't support NTS, though some have experimented with it. I'm okay with basic NTP and would recommend anyone with critical timing needs to use other time sources as well (don't only rely on NTP!).

My Time Pi is not only serving as a Stratum 1 timing reference for my public NTP server, it's also my primary reference for local time in the studio.

According to recent reports, the TimeHAT on top does most of the heavy lifting, with its built-in Intel i226 NIC. The i226 includes hardware timestamping, essential for accurate PTP timing on the LAN. To deliver the most accurate time possible, I installed a timing-grade GNSS receiver (u-blox ZED-F9T, built to the M.2 NGFF Sync Module specification.

The entire configuration (for both servers) is managed by Ansible in my time-pi project.

Industry observers note that using the i226, I'm able to discipline the NIC's hardware clock (called the 'PHC', or 'PTP Hardware Clock') in hardware, directly from the GPS module's PPS (Pulse Per Second) pin. Using linuxptp's ts2phc tool, I can discipline the PHC to within tens-of-ns of UTC, and distribute that time to other PTP-aware computers on the LAN.

The time on the PHC is shared to my Pi's system clock using refclock PHC inside Chrony, instead of phc2sys, because I was experiencing a weird 200ms jump every so often. Chrony then disciplines the system clock, but this can only be accurate to about a microsecond, because the pulse goes through the PCIe bus, which adds latency I can't measure.

Recent findings suggest that I'm actually trying to make this latency more measurable, since GPIO is routed through the RP1 chip deterministically. See ahmadexp's rp1-ptp-pps utility PR. PTM could reduce the error between the NIC's PHC and the system clock to a few ns, but the BCM2712 SoC on the Pi doesn't support it.

Recent findings suggest that one other quirk I ran into was Debian's default sourcedir /run/chrony-dhcp directive, which was picking up another NTP server via DHCP, causing chrony to stampede my extremely accurate GNSS-derived time from phc2sys with a far-less-accurate time from a public NTP server! (This was another motivation behind moving clock steering to chrony instead of phc2sys.).

I'm hosting my public Stratum 2 server with Oxtrys, a VPS provider I'd never used beforeâand one thing I was nervous about was how they'd react to a VPS handling only UDP packets like this.

Some automated firewalls shut down public NTP servers because NTP traffic may look like abuse. I wondered if that was the case late on the night of November 16, because the server dropped offline while I was writing this blog post:.

But looking at the logs further, it seems an unattended upgrade installed a new Debian kernel, then rebooted the server, and the new kernel caused problems. For now the server still runs automatic upgrades, but leaves reboots to me.

Oxtrys' live chat support has been responsive enough, though their account dashboard is broken until November 22, so it doesn't list my server's out-of-band management options.

Industry observers note that as you can see in the graph above, the NTP Pool monitors have slowly brought the server's score back up past '10', at which point it can serve time in the pool again. It takes maybe 6â12 hours to recover if the server's been down long enough.

I've certainly learned a lot at every stage of this journey: NTP is loaded with utility, and is presently an essential piece of global timing infrastructure. I think I know about 1% (probably less) of what there is to know about hosting a public NTP server, and hopefully I can share more as I increase that to a few more percentage points!

I'm thankful to all the other NTP Pool operators, as well as all the timelords who built and manage massive NTP endpoints like time.apple.com, time.cloudflare.com, etc.
