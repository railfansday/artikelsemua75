We ran one resume through 20 layouts and a text extractor: here is what got lost

📑 Quick Jump: 1. Overview • 2. Key Details • 3. Closing Notes

This tests text extraction, not any employer's applicant tracking system. We did not run Workday, Greenhouse, Lever or any other ATS and cannot say how they behave.

Patch 2026-11-19: after this test we fixed two things in our own checker, so its scores moved. It now counts Word list items, numbered lists and ➤ or dash markers as bullets (pull requests #123 and #118 in our repository). We re-scored the same files: the DOCX baseline, DOCX table layout and DOCX two-column table go from 90 to 100, the DOCX header and footer files from 70 to 80, and the ➤ PDF from 90 to 100. The table highlights the 2026-11-17 score and the score now. What each extractor lost did not change, and we re-ran six of the files through the live checker on 2026-11-19 to confirm.

In a recent development, we wrote one fictional resume ("Jordan Sample": 228 words, four sections, nine bullets, ten skills) and generated 20 versions of it. Only the layout changed: single column, two-column sidebar, table layout, different bullet styles, emoji icons, letter-spaced headings, unusual heading names, a ligature-heavy serif font, absolutely positioned blocks, contact details as an image or as link labels, headings as images, and a full-page image. (Related: Breaking: How to generate text: using different decodin...)

Recent findings suggest that for each file we extracted text and looked for 37 items: name, email, phone and link; role, company and dates for three jobs; the education line; ten skills; a certification; the summary; and all nine bullets as unbroken sentences. We then ran the CVPosh ATS checker's scoring code on the extracted text.

PDFs were extracted with pdf-parse 1.1.1 and DOCX files with mammoth 1.11.0, the libraries the checker uses. "Order" counts how many of 10 landmarks in the resume (summary, employers, bullets, education, skills) appear in the expected sequence.

Raw numbers for both extractors are in the results CSV.

Four files lost email, phone and link together: the contact line as an image, the contact line as link labels ("Email me", "Call me") with the real addresses only in link targets, and contact details in a DOCX header or in a DOCX footer.

In the link-label PDF the address exists only as a link annotation, and neither pdf-parse nor poppler's pdftotext returned it. For the DOCX files, mammoth returned the body only; in the header file even the name was gone because we had put it in the header too. In the checker this cost 20 points each (15 for no email, 5 for no phone). A contact line in the page body, as plain text, was extracted by every method we tried.

It has been revealed that also: in the two-column PDF the LinkedIn URL wrapped at its hyphen inside the narrow sidebar. pdf-parse returned jordan- and sample on separate lines and pdftotext dropped the hyphen (jordansample). The checker still saw a link, but not a working URL.

It has been revealed that the checker looks for experience, education, skills and summary or profile. Three PDFs fell to 1 of 4 sections:.

In a recent development, each cost 20 points. The bigger risk is any system that groups your history by section: it has to recognise the header first. (Related: Porting fairseq wmt19 translation system to transformer...)

The two-column sidebar, the DOCX two-column table, the positioned-blocks PDF and the CSS-drawn-bullets PDF kept every word, but pdf-parse changed the order:.

pdftotext re-sorted the CSS-bullet and positioned-block files into correct visual order (10 of 10). So the problem is partly the file and partly the extractor, and we cannot tell you which one an employer's system resembles. The score did not move: the checker has no reading-order rule, so the two-column PDF and the positioned-blocks PDF both scored 100. A checklist can show that data is present, not that it is in the right place.

A table layout (dates in one column, roles in the other) extracted in order as PDF and DOCX. A Palatino font with ligatures enabled returned normal text, including "Airflow" and "Certified". Emoji next to contact details left the values intact, although they came out as private-use characters in pdf-parse. A ➤ bullet was extracted as a character.

According to recent reports, we found this while testing. The checker counted a bullet only when a line started with •, - or *. A DOCX with real Word list bullets scored 90 and the same file with typed "•" scored 100, because mammoth does not put list markers in its raw text. The ➤ PDF also scored 90. So the checker deducted 10 points from resumes whose bullets read fine. We fixed both after the test: the same files now count 9 bullets and score 100. Two things remain. The CSS-drawn-dots PDF still scores 90 because its bullets are shapes, not characters, so the checker sees none. And the score can still disagree with a real parse in the other direction: contact details in a Word header or footer still cost 20 points (80 against 100 for the body version), and the checker still has no reading-order rule.

Does an ATS reject resumes with columns? We did not test any employer ATS, so we can't say. In our extraction every word of the two-column files survived, but the reading order changed.

It has been revealed that is DOCX safer than PDF? Not in our test. DOCX avoided the ordering problems but was the only format where header and footer content disappeared.

Do icons hurt? Icons next to text did not remove the text. Text drawn as an image did.

In a recent development, does a high checker score mean my resume will parse correctly? No. The checker starts at 100 and subtracts points when a rule fires, and it has no reading-order rule. Three layouts with changed order still score 100.

Industry observers note that is this representative of real templates? No. It is one synthetic resume laid out by us in Chrome and a DOCX library. Word, Google Docs, Canva or LaTeX output can behave differently. Treat the results as a list of things to check, not as rates.
