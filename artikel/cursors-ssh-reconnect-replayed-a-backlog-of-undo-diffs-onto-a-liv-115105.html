Cursor's SSH reconnect replayed a backlog of undo-diffs onto a live workspace

In a recent development, A Cursor user working over Remote-SSH into a Linux GCP VM had their SSH connection drop and auto-reconnect mid-session. Six seconds after the client reconnected, files across two repositories on that remote started rewriting themselves.

In a recent development, per the original forum report, the reconnect caused cursor-server to replay a backlog of pending "Undo Create Diff" operations against the live workspace: 56 history writes landed within two seconds of the reconnect, followed by a mass file-modification-time rewrite about six seconds later. New gitignored files in a sandbox folder came back empty, and tracked files — in that repository and in a second, unrelated repository on the same VM — were rewritten too. (Related: Second Circuit denies Kalshi and Coinbase interim relie...)

In the original report, git-tracked content still matched HEAD, and the gitignored files were eventually restored from Local History after a second reconnect synced the workspace back up — a full recovery, but a manual one. Two other users hit the identical bug in the same thread over the following weeks. One, on August 4, had 100-200 files rewritten in roughly seven seconds and reported many had no Local History snapshot to fall back on — an unrecoverable loss. A third, on August 7, recovered via an agent chat session instead. (Related: Geren reopens Texas casino fight, but his amendment sti...)

Cursor staff (Mohit, then Colin) confirmed the behavior was unintended, requested logs, and tracked it for over three months. On November 6, 2026, Colin reported a shipped fix: restoring pending Agent changes after a reconnect or reload no longer rewrites or deletes files on disk, and a dropped connection can no longer leave behind bad checkpoint data. The original reporter confirmed no recurrence since.

The thread documents three users hitting the same failure mode, not a count of how many were affected in total, and there's no vendor postmortem beyond staff replies in the forum — just acknowledgment, tracking, and a fix. It's also not clear from the thread exactly which checkpoint-restore code path caused the 100-200-file case specifically, versus the more contained original report.

This wasn't one person's fluke setup. The same trigger — a dropped-and-restored SSH connection to cursor-server — produced the same effect for at least three separate owners over several weeks: a backlog of pending undo state gets replayed against files that were never part of that backlog, sometimes with no local snapshot available to undo it. If you were running Cursor's Remote-SSH against a Linux VM before November 2026 and have ever had a connection drop mid-session, it's worth checking whether anything in your workspace highlights the same reconnect-timed rewrite pattern Cursor fixed — the fix means new sessions should be safe, not that any damage already done was found.
