Most multi-tenant SaaS backends isolate customers like this:.

It works until the day someone forgets the where. A fresh endpoint, a raw query for a report, a background job, a tired developer, an AI assistant that "simplified" the query. One missing filter and customer A sees customer B's data. Code review won't catch every one, and tests usually check the happy path.

Industry observers note that postgreSQL has a better place for this rule: Row Level Security (RLS). The database itself filters every row, for every query, including the ones you forgot about. (Related: Industry News: Simple considerations for simple people ...)

Recent findings suggest that but RLS has sharp edges. Done half-way, it gives you a false sense of safety. This post walks through the four things you need to get right, with NestJS and Prisma 7, and the tests that prove it.

In a recent development, here is the trap many tutorials skip: RLS does not apply to the table owner or to superusers. And in many projects, the app connects with the same user that ran the migrations, which is the owner. (Related: Tech Report: Showcase Your Projects in Spaces using Gra...)

So the policy exists, the tests pass on your machine, and it filters nothing.

The app uses APP_DATABASE_URL (as app_user). Migrations use DATABASE_URL (the owner). And the app checks this at boot, so a wrong env var fails loudly instead of silently turning isolation off:.

You tell Postgres the current tenant with set_config. The third argument matters a lot:.

In a recent development, true = local to the transaction. At COMMIT or ROLLBACK the setting is gone. With false (session level), the setting stays on the pooled connection, and the next request that gets that connection runs as the previous tenant. That is a data leak that only demonstrates up under load.

Now service code has no tenant filter at all:.

Industry observers note that withCurrentTenant reads the tenant from an AsyncLocalStorage set once per request, so it survives every await and concurrent requests never mix. Outside a tenant context it throws, instead of quietly returning nothing.

There is a chicken-and-egg problem. To authenticate an API key you must read api_keys. But api_keys is under RLS, and you don't know the tenant yet, so you see no keys.

The two common "fixes" are both bad: query with the owner connection (now your app holds an RLS-bypassing connection), or trust an X-Tenant-Id header (now the client picks its tenant).

The app can call one function that takes a hash and returns one tenant id. It cannot read any key. A global NestJS guard calls it, sets req.tenantId, and an interceptor runs the handler inside that tenant's context.

Plus revision, delete, moving a row to another tenant, raw SQL, and 20 concurrent transactions of two tenants.

And one more test that I think every RLS project needs: a privilege audit. It lists every table in the schema with the exact grants the runtime role should have, and checks that every table with a tenant_id column has ENABLE + FORCE + a policy with both USING and WITH CHECK. If someone adds a table and forgets RLS, CI goes red.

To check the tests themselves, I turned RLS off on one table: 15 tests failed. That is the point.
