On 19 November PHP shipped 8.5.13, 8.4.28, 8.3.37 and 8.2.36, alongside the first stable 8.6.0. The 8.3.37 changelog lists 13 security fixes. Five of them are rated critical, every one at 9.2 on CVSS v4. My production server, a single Ubuntu box with several sites behind nginx and PHP-FPM, was still on 8.3.36 the next morning. It has been revealed that I patched it. But first I read every critical advisory and asked one question of each. What would an attacker need from a Laravel app for this to work?

In a recent development, the answer surprised me a little. Most of them need something a stock Laravel app never does. And the ones that could still matter depend on what else shares the server, not on Laravel. One setting even changed during the upgrade, although nobody touched php.ini. The release announcement is short. It says this is a security release and encourages all 8.3 customers to upgrade. The detail lives in the changelog and the php-src security advisories. Three of the five critical fixes are in ext-session, PHP's own session extension. One is in ext-date and one is in PHP-FPM.

In a recent development, so for each fix, the question becomes concrete. Does the bug need PHP's native session machinery, a specific php.ini, or a specific web server setup?

In a recent development, the other eight fixes in the 8.3 branch cover SOAP, Phar signatures, the FPM status page, PHP-CGI and the HTTP stream wrappers. Four of them are rated high. Worth patching, but none of them is the reason to patch today.

It has been revealed that the serializer mismatch is the one with the scariest headline, so I started there. PHP's session upload progress feature tracks a running upload by writing progress data into the visitor's session. The PHP manual says plainly when that happens. "The upload progress information is written to the session before any scripts are executed.".

Recent findings suggest that that's only half the attack, though. The advisory needs a second step, something that reads the same stored session with a different serializer and then deserializes it with a gadget chain available. In a Laravel app nothing reads /var/lib/php/sessions. Laravel's file driver writes to storage/framework/sessions through its own handler.

Recent findings suggest that so what reads native sessions on a typical Laravel server? Usually nothing. On my box the native session directory was empty:.

But a server that also hosts a WordPress site, an old admin panel or a phpMyAdmin install is a different story. Those use native sessions. The partially overwritten session files bug needs the same thing, native file sessions with attacker influence over the data.

Sources indicate that the interrupted shutdown use-after-free is the subtle one. It's an incomplete fix for one of October's advisories (CVE-2026-109619), and it claims outright that disabling upload progress does nothing for it. It needs a native session whose cleanup hits a fatal error. Then the next request on the same FPM worker touches freed memory, and that request doesn't need to belong to the same user or the same site. My server runs every site in one FPM pool called www. So if any of those sites used native sessions, a Laravel site sharing the worker would inherit the problem. The advisory says it could lead to code execution, although that hasn't been demonstrated yet. But "shared worker" is exactly the kind of detail I'd rather not argue about.

Sources indicate that PHP reads php://input lazily. If a code path opens the stream and stops early (the advisory's example is a malformed multipart body that makes PHP's parser stop at a predictable position), the rest of the body stays unread on the connection.

In a recent development, on a normal nginx setup that's harmless. nginx closes the FastCGI connection after each request, and the leftover bytes go with it. With persistent connections they don't. The leftover bytes get parsed as the next FastCGI request, and an attacker can forge its parameters, including PHP_ADMIN_VALUE settings like auto_prepend_file.

So the check is one grep. Is anything keeping FastCGI connections open?

Industry observers note that no output on my server. fastcgi_keep_conn defaults to off, so every site there closes the connection after each request. The advisory also names Apache's mod_proxy_fcgi with enablereuse=on, HAProxy FastCGI backends and LSAPI. If you run any of those, this is the fix to apply first.

Sources indicate that the Laravel side helps a little too. Symfony's Request::getContent() reads php://input to the end with file_get_contents(), unless you explicitly ask for a stream resource. But the advisory warns that reading the whole body may not be a reliable mitigation on its own. So the front end setting is the one I'd check.

According to recent reports, the server uses Ondřej Surý's PPA, so the fix arrived as 16 php8.3 packages. I wanted three things. A way back, no surprise config changes, and proof afterwards that every PHP process was on the new binary.

The dry run showed 16 upgrades, nothing new installed and nothing removed.

Industry observers note that ubuntu's needrestart saw that supervisor's children were running the old PHP binary and restarted supervisor on its own. That restarts every queue worker on the box. It's the right outcome (a worker on the old binary is still unpatched), but it happens mid-upgrade, whether or not a job is running. Laravel workers finish the current job when they get SIGTERM, as long as supervisor's stopwaitsecs is longer than your slowest job. I wrote about that in what happens to a running job when the worker stops. Check that setting before you patch, not after.

In a recent development, the compiled default flipped. The serializer mismatch advisory says the fix disables session upload progress by default, and the binary agrees. The configuration page of the PHP manual still says it defaults to 1 at the time of writing, so don't trust the manual for this one. Trust php -i. I'm keeping the explicit Off for FPM anyway. A default can flip back on a rebuild, a different PPA or a different branch, and an explicit line in conf.d survives all of them.

None of this is a reason to wait. "My Laravel app doesn't reach it" is true for a clean server, and very few servers stay clean. A second site in the same FPM pool, a forgotten phpMyAdmin, someone enabling fastcgi_keep_conn for a benchmark next year. Each of those quietly turns a "no" in that table into a "yes".

Recent findings suggest that what the analysis does tell you is where to look while you patch. Three checks cover most of it:.

Sources indicate that the first finds persistent FastCGI connections. The second indicates the upload progress setting, where native sessions live, and whether startup warnings go to a file (the timezone bug needs that). The third tells you whether anything on the box uses native sessions at all.

It has been revealed that my own answers were no keep-alive, upload progress off, and an empty session directory. error_log is unset, so startup warnings go to FPM's own log, which the timezone advisory says doesn't meet its condition. So the box wasn't exposed to the demonstrated attacks, and it's patched now regardless. The rest of that server's setup is in how I hardened my VPS with SSH keys, Cloudflare and Tailscale. For the dependency side of fast security fixes, see Composer 2.11's cooldown, which holds back security releases too.

What I'm changing next is the one-pool-for-everything setup. With a separate FPM pool per site, a native session in one app can't leave freed memory for a request from another, and the interrupted shutdown bug would never have been a question.
