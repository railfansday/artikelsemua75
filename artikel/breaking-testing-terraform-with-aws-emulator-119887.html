In a recent development, terraform initiative passes and demonstrates all green and all the necessary resource changes. You trigger apply and... the job fails with some obscure error that a resource can't be changed. You open another pull request and try again. And perhaps you encounter an error again. Sounds familiar? I bet it does. I encountered issues like this so many times I'm afraid to count. But recently AWS released a new tool called Emulator that emulates actual AWS API endpoints. And it should be great for tasks just like that!

The problem with the difference between initiative and apply jobs is that plan can't possibly emulate every actual API call against a live infrastructure. It's a safe assumption based on the static declarations we put into it – the order of application, the necessary parameters, the proper configuration values. These mock calls can't know for a fact that you already have a resource in AWS called "my-bucket-asdasdasd" or that you're trying to upgrade a PostgreSQL RDS instance from version 14 to version 18 without an explicit "apply immediately" flag. One may argue that one can always try to apply changes locally, but this kinda undermines the whole automation workflow. So what is the answer? (Related: Tech Report: Transformer-based Encoder-Decoder Models...)

There are multiple tools that can emulate AWS services either partially or in full, but what they lack is the actual knowledge of the service architecture. It may be similar, but it won't be authentic, and sometimes this small difference may cause a lot of problems. After all, what can be the closest to an AWS API, if not the same AWS API, but ephemeral?

In a recent development, the benefit of the AWS Emulator is that it's a self-contained binary (or Docker container) that can be utilized locally or in a CI workflow. This means the usual "Initiative > Apply" terraform workflow changes to "Plan > Apply against mock AWS infrastructure to test the plan > Apply on actual AWS Infrastructure". This means slightly longer jobs, but if you're like me and apply jobs run on commits to the main branch after a PR, this saves you the hassle of creating a fresh branch just to fix the concern.

Industry observers note that AWS Emulator is AWESOME. I'm rarely that excited about newly introduced tools lately (mostly because almost all of them are near/about AI), but this one is just so good and scratches that exact itch I felt for so long.

Industry observers note that for starters, it can't effectively emulate IAM policies and permission checks. This is a bummer, because permission validation is such a crucial step for production-ready security. Here's hoping that the tool will evolve further and it will be included in future updates.

Sources indicate that second, as a tool still a work-in-progress[1], its capabilities are quite limited. Even while writing the article I encountered several cases of 501 NotImplemented. It complicates things a bit if your infrastructure setup is huge and has a lot of quirks and weird configurations and super upcoming services. Still, AWS releases new versions quite often, and they're quite open about Emulator limitations, which is nice.

In a recent development, and last, but not least, is telemetry. AWS is explicit that it gathers telemetry and what this telemetry includes. This is honest behaviour and I like that approach. They even allow you to disable the telemetry, which further increases my trust in this tool. I understand the rationale behind this functionality (the tool is actively developed, they need the data to understand usage patterns and what goes wrong), but in the age of constant surveillance from Major Tech at every corner it still raises a slight concern. But then again, for the ultra-paranoid folks the code is open source and can be rebuilt with telemetry torn out of it.
