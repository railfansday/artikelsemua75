aws events test-event-pattern checks a pattern against a sample event without creating anything. This is how I tested the sign-in rule:.

According to recent reports, I ran nine cases across the two rules. Root sign-in, IAM user without MFA, StopLogging and CreateAccessKey matched. An IAM user with MFA, a failed login, a single sign-on session and DescribeInstances did not.

According to recent reports, 1. IAM lives in us-east-1. IAM, STS and CloudFront are global services, and CloudTrail records their events in US East (N. Virginia). A rule in eu-west-1 will never see CreateAccessKey. Root sign-ins land in us-east-1, us-east-2 or us-west-2. Deploy the stack in us-east-1, then in those two, then in every Region you run workloads in.

In a recent development, 2. MFAUsed is always No for single sign-on. AWS only sets it for IAM people and root. Without the IAMUser filter, every SSO login emails you.

It has been revealed that 3. S3 event names differ from the API. The API call DeletePublicAccessBlock appears in CloudTrail as DeleteBucketPublicAccessBlock or DeleteAccountPublicAccessBlock. Match the CloudTrail name.

Sources indicate that 4. Read-only calls need a different rule state. A rule in the default ENABLED state does not match read-only management events. To alert on something like GetSecretValue, set the rule's state to ENABLED_WITH_ALL_CLOUDTRAIL_MANAGEMENT_EVENTS. You also need a trail that is logging, or none of these rules receive anything.

Recent findings suggest that one more: the docs spell the sign-in detail-type two ways (AWS Console Sign In via CloudTrail and AWS Console Signin via CloudTrail). The pattern above matches on source: aws.signin so it does not depend on either.
