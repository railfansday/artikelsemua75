Quick status check before anyone gets ahead of me: nothing has been flashed yet. This post is about the strategy and the prep work, not a victory lap. If you came from part 2 expecting "and then I fixed it," this is the "and here's why that's harder than it sounds" post instead.

Recap: the box in question turned out to be infected with a BadBox-pattern dropper — fake-Google-named packages, a persistent root daemon, SELinux left in permissive mode. The malicious apps are removed, but that was always treating a symptom. The actual fix is replacing or cleaning the firmware itself, and that's a much less reversible operation than uninstalling an app. (Related: Breaking: My Journey to a serverless transformers pipel...)

So before any of that happens, step one is: back up everything.

In a recent development, the board inside this thing is an Allwinner "homlet" SoC, and it's Project Treble–compliant — which matters a lot here, because it means the device uses dynamic partitions (the super partition scheme, logical partitions carved out of it instead of fixed physical ones) plus AVB (Android Verified Boot). That combination raises the stakes on a botched flash: get the partition layout or the verified-boot chain wrong and you're not looking at "reflash and try again," you're looking at a brick.

Which is exactly why nothing gets written until everything's backed up first.

Industry observers note that before touching anything, I pulled a full backup of the partitions that matter: bootloader, recovery, misc, vbmeta, vbmeta_system, vbmeta_vendor. If anything goes wrong later — wrong image, bad flash, anything — there's a known-good copy of the box's original state to fall back to. This part's done. (Related: Industry News: Simple considerations for simple people ...)

Here's where "in progress" actually means in progress. The obvious move for Allwinner silicon is FEL mode — Allwinner's USB boot-ROM recovery mode, the standard low-level way to get a fresh image onto this kind of board over a USB cable, no OS cooperation required.

That's not available on this hardware. The USB-C port on this particular box is wired for power only — no data lines to the SoC's USB OTG controller, which means no FEL, full stop. Whatever this specific device's board design does with FEL mode, it's not reachable through the port you'd normally use for it.

In a recent development, so the alternative being evaluated now is an SD-card based update — the mechanism a lot of these Allwinner-based boxes support for applying a full system update by booting from a prepared SD card instead of over USB. That's the path I'm presently investigating: whether this board's bootloader will actually pick up and apply an update from SD, and what exactly a valid update package needs to look like for it to accept one.
