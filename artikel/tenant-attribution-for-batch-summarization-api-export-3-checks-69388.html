Sources indicate that an e-commerce hiring service needs to explain which tenant paid for summarizing each candidate's documents before those summaries enter a job-rubric scoring workflow. A completed async job doesn't answer that question. Neither does a downloadable file.

In a recent development, TL;DR: Queue multiple documents for batch summarization, keep one summarization prompt across items, and preserve an application-owned tenant-to-item mapping through result collection and export. Make three checks before candidate scoring: every result belongs to a submitted item, every submitted item is accounted for, and every attributed cost has an explicit source and scope. Before: a web request loops through candidate documents, collects summaries, and leaves someone to reconcile the bill afterward.

In a recent development, after: the request hands off a batch. The application retains the relationship between tenant, candidate, document, and submitted item. Processing happens asynchronously. Result collection and the administrator's download are separate steps.

Industry observers note that diagram in words: tenant submission → item ledger → async batch → status polling → result reconciliation → candidate review and export. Cost evidence joins the ledger at the scope where it was actually reported.

It has been revealed that A batch-level amount cannot establish each document's actual charge. Dividing a total evenly might be an allocation policy, but it isn't an observation of individual calls. For an illustrative dataset, imagine two tenants, three candidate documents, and one rubric version. Two documents belong to one candidate at shop-a; the third belongs to another candidate at shop-b. If one submission processes all three, copying its entire reported cost to each tenant would count the same amount twice. Dividing it by three avoids that particular duplication but still makes an assumption about the cost of each document. Neither operation discovers a missing observation. The export should label an allocation as an allocation and preserve its policy separately from observed cost evidence.

Those numbers are example inputs, not production measurements.

It has been revealed that keep the rubric version alongside the summarization prompt version so reviewers can identify the transformation that produced their evidence. Use the same summarization instruction across items; candidate documents supply the variable content. That makes output shape more consistent and easier to parse.

In a recent development, this read is safe to retry. It honors Retry-After as either seconds or a date and uses exponential backoff when retrying a rate-limited request. Four attempts bound the example.

Submission is a separate operation. For writes, use the documented idempotency convention so retries do not create duplicate work. A retry policy and a deduplication policy solve different problems.

Recent findings suggest that once the adapter exists, teach reconciliation with the three-document fixture above. Return the results in a different order from submission. Join by an explicit submitted-item identifier, reject unknown identifiers, and identify duplicates before exporting. A result at array position zero must not inherit the tenant at submission position zero.

Keep the application ledger authoritative for ownership.

Recent findings suggest that for the third check, retain the source and scope of each cost observation. If the integration has only a batch-level amount, keep it at batch scope until an explicit allocation policy applies. A missing item-level amount remains unavailable; zero would assert something different.

Recent findings suggest that batch submission is the easiest backend pattern for a beginner summarizing many documents at once. Queue the collection, poll status, collect outputs after completion, and request downloadable results for the administrative workflow.

Industry observers note that the direct provider options deserve evaluation when those providers are already candidates for the underlying model work. The shared REST interface fits a team that wants an HTTP integration and inspectable schemas across backend capabilities. This is an integration decision, not a measured performance ranking. Model suitability for rubric evidence still requires its own evaluation.

Export is a delivery step. Compare collected identifiers with the submission ledger before presenting a download as complete. In the illustrative fixture, all three documents must be accounted for, including both documents belonging to the same candidate.

Recent findings suggest that there is a useful trade-off here. Refusing an incomplete collection makes the invariant easy to teach. Retaining partial progress is friendlier for a large administrative job, but the interface must identify missing items and avoid calling that collection ready for complete scoring. An export intended for reviewing summaries can disclose unresolved cost attribution. An export intended for tenant accounting needs that gap resolved or explicitly recorded under an agreed allocation policy.

According to recent reports, for observability, track missing summaries and missing attribution separately. A completed-job count answers an operational question; a reconciled-document count answers another. Do not let either silently stand in for accounting completeness.

Sources indicate that they help keep summary shape consistent and easier to parse. They do not prove that summaries preserve all relevant evidence or that subsequent scores are valid.
